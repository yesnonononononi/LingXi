## 追加：用户质疑「框架适配补丁」归类，复核后我承认错误归因（22:25）

用户指出两点，**均成立**：
1. **不需要框架返回 executionId** —— `AgentRequest.executionId` 的 javadoc 原文是 "Optional **caller-provided** identifier for this single execution"（`AgentRequest.java:18`）；`Execution.create` 非空即采用、为空才回落 `UUID`（`Execution.java:70-72`）；本项目 `RequestPreparer.buildRequest` 一直显式传入。框架从未返回 id。
   - ⚠️ 顺带纠正：`AgentRequest` **没有 `requestId` 字段**（`requestId` 只在 `ToolCallStartEvent`/`ToolCallEndEvent`）。
2. **不需要给 `Execution` 加 `modelName`/`provider`** —— `Execution.getAgentRequest().getModelConfig()` 就是本次实际生效的配置，直接有 `modelName`/`provider`；而 `LocalExecutionRepository#applySummary` **用的正是这条路径** → 我自相矛盾。

**重新校准结论**：原 8 条「框架适配补丁」里**只有 1.5 条真与框架契约耦合**：
- 真耦合：摘要列必须寄生在框架 SPI `LocalExecutionRepository#save()` —— 运行期唯一能反复拿到完整 `Execution` 的钩子（改挂终态 `RuntimeListener` 会丢失进行中的 `started_at`）。
- 半条：`startAt` 的「恢复不重置」是框架现有行为语义。
- 其余降级：P2/P4 = 业务读业务自己的数据；P5/P6/P7/P8 = 业务侧设计选择（INT 存状态码 / BIGINT 主键 / 在自己的表上登记初始行）；P1 = 本仓历史债。

**教训（重要，避免复发）**：**不要把「业务读自己写入的数据」包装成「框架缺口」**。判断标准：如果数据是业务自己塞进 `AgentRequest`/`attributes` 的，读回来就是正常写法，不构成框架依赖。文档 §7 原表已整表作废并在文末留删除记录。
- 另：`agentId → agent → model` 反解模型名**不可用于快照** —— Agent 换绑模型后历史名会跟着变，违反验收 #12；且真库 `execution` 无 `agent_id` 列，得走 `attributes[lingxi.agent_id]`。

## 追加：用户提出 chat_turn 与框架 execution 解耦，评估结论（22:38）

**用户提案**：新增业务侧 `chat_turn` 表（id 雪花 / session_id / parent_turn_id / **execution_id 可空 + 唯一键** / status 六值 ACCEPTED·RUNNING·WAITING·COMPLETED·FAILED·CANCELLED / model_name·provider / 三列 token / started_at·completed_at），语义切分为：**框架 execution = 运行时快照记录（提供可回滚能力）；业务 chat_turn = 业务上最权威的用户单次请求记录**。把耦合 executionId 的点全部换成 turnId。

**评估结论：方向正确，8 条补丁消除 6 条 + 我标为「真耦合」的那条也消除。**
- 消除：P7（预插执行行，本质就是「借框架的表存业务概念」）、P8（启动失败收口）、P2（modelName 反解 → 改由业务在 turn 创建时从自己的 RuntimeContext.modelConfig 写）、P3（startAt 语义依赖）、P4（root_execution_id → parent_turn_id 一等列）、P1（init.sql 漂移的根因消失：框架表回到 6 列）、真耦合（摘要不再寄生 `LocalExecutionRepository#save()`）。
- 大幅减少：P5 状态码映射 5 处 → 1 处（展示改用 chat_turn.status；框架控制仍需 execution.status）。
- 不变：P6 String↔Long 双口径（框架 SPI 签名就是 String executionId）。
- 额外收益：`ExecutionIdentity` 的 5 个 DB 方法 + `ExecutionQueryService.latestStatesBySession` 基本溶解（业务问题不再靠读框架表回答）；`uk_chat_turn_execution` 让 executionId→(轮次+会话) 变成一次唯一键查询；验收 #9 天然成立。

**3 项新代价（必须讲清）**：
1. **R1 双状态机一致性（最高）**：`execution.status` 今天是框架在写 snapshot 的同一个 save() 里写的，**不可能与快照漂移**；改后若让业务把「控制决策」（能否 resume/cancel）改判 `chat_turn.status`，就引入新失效模式 —— **钩子漏触发 = 那次执行再也恢复不了**。**建议分工：chat_turn.status 权威用于展示，execution.status 权威用于控制。**
2. **R2 收尸点从 1 处变 2 处**：chat_turn 也会残留 ACCEPTED/RUNNING，需与 `markOrphanRunsFailed` 配套。
3. **R3 代码总量不减反增**（删 2 服务+若干方法，增 chat_turn 的 PO/Mapper/Repo/领域/服务/监听约 6-7 文件）—— 要用「依赖方向对不对」评估，不是「少写多少代码」。

**DDL 3 条意见**：① `uk_chat_turn_execution` 唯一键会把「重新生成」锁死（届时一轮 N 执行），需明确接受并注释；② `WAITING` 与框架 `SUSPENDED` 的映射要写进注释；③ `started_at` 取框架 onStart 时刻（纯执行）而非 ACCEPTED 时刻，与计划「总历时含等待」口径一致。

**实施建议**：不要在当前未提交的工作树上原地变形。分 S0（跑通并提交当前形态作基线）→ S1（建表 + 双写 + 历史接口加 turns 字典）→ S2（读路径切 turn、删除 P7/P8 与 execution 的 8 个摘要列）。
