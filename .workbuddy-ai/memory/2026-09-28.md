## Agent 邮箱路由重设计（按 docs/design/20260928-agent-mailbox-routing.md 实施）

- SQL：`init.sql`、`db/manual/20260928_create_email_tables.sql`、新增 `db/manual/20260928_migrate_email_routing.sql`（扩展—回填—切换—收缩，含备份/重复邮箱合并/幂等守卫）、`src/test/resources/email-schema.sql`

## 追加修复：loop 恢复后子 Agent 起不来（TEAM_ID 丢失）

**症状**：挂起前 `call_sub_agent` 能委派，恢复后报「未确定当前协作团队，无法委派任务」，子 Agent 起不来。

**根因（已用 `git show HEAD` 证实，非推测）**：`RequestPreparer.attributes()` 在 HEAD 版本**根本没有写 `TEAM_ID`**（团队绑定当时走 ThreadLocal）。属性化是本次未提交重构才加的，因此**升级前写入的所有执行快照天然缺少 `lingxi.team_id`**。而恢复链路**不经过 `RequestPreparer`**，三条恢复入口都是「读快照 → 直接交给 loop」：
- `ChatServiceImpl#resume`
- `ToolCallServiceImpl#decideDecision`（plan / choice 决策）
- `CommandApprovalExecutor#finish`（命令审批）

→ 快照缺属性，恢复后委派工具解析不到团队。

**修复**：新增 `com.summit.dp.execution.SessionAttributeRestorer`（`@Component`），在**三条恢复入口**把会话行的 `team_id` 补回 `AgentRequest.attributes` 再交给 loop；以库中记录覆盖快照值（与 `RequestPreparer` 的「已有会话以库中记录为准」同口径）；会话无团队时不写入，不凭空制造团队身份。补回的属性随恢复过程的检查点落库，**旧快照因此自愈**。

**新增测试**：`ChatResumeTeamAttributeTest`（3 例，`com.summit.dp.agent.application.service.impl`）——断言落在 `ExecutionControl.resume(Execution)` 的**实参**上（`resume(String)` 返回副本，断言副本无意义）：补齐缺失的 TEAM_ID、覆盖陈旧 TEAM_ID、非团队会话不写入。

**注意**：`CallSubAgentTool#buildRequest` **故意不给子执行带 `TEAM_ID`**（与 `delegatedTools` 双保险）。所以若故障发生在「被恢复的子执行」上，本次修复不覆盖——那需要先决定是否给子执行下行团队身份。另外 `CallSubAgentTeamResolutionTest` 的 javadoc 声称「resume 后同样解析正确」，但它只单测了 `resolveTeamId`，从未真正跑过恢复链路——正是这条失实的守卫注释掩盖了缺陷。

**最终验证**：`./mvnw.cmd -o test` → **150 通过 / 0 失败**。
