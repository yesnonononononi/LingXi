**核心架构结论**

**安全结论**：No-Go。19 条硬约束（P0=10 / P1=9）。

## 框架职责边界尽责性 + 分布式就绪度评估

**产出**：`deliverables/gstack/arch-review-boundary-distributed-2026-09-27.md`

**问题一：边界是否尽责** → 🟡 基本尽责但有缺口（6.4/10）。判据：C1 声明一致 7 / C2 边界内完整 7 / C3 接缝充分 6 / **C4 无空头承诺 5** / C5 演进 7。
- 边界选择**站得住脚**：与 LangChain4j / Spring AI 的「机制 vs 产品」哲学一致，非异类。单 loop 是唯一无法在业务层可靠重建的部分，multi-agent 可用「多个 Agent 实例 + 自建调度器」组合。
- 缺口：G1 `harness-memory` 零类却签名发布（空头承诺，严重）；G2 `ExecutionRepository extends ActiveExecutionRegistry` 混职责；G3 恢复注入反馈是隐式契约（终态 `List.copyOf` 冻结 messages）；G4 事件扇出无寻址；G5 `task`/`attributes`/`TypedEvent` 悬空。
- **不该加进框架**：multi-agent 编排语义、memory 策略存储、业务决策模型、会话持久化/分布式锁、事件路由基础设施。

**问题二：是否原生支持分布式** → 🔴 不原生支持。本质是「无状态计算内核 + 进程内状态 + 可替换接缝」。
- ✅ 计算无状态水平扩展成立（`AgentRequest.messages` 自带全量上下文，runtime 从不按 id 加载历史）
- ⚠️ 跨节点 resume 条件成立（需应用提供共享 `ExecutionRepository`）
- ❌ 跨节点 suspend/cancel、跨节点事件/SSE、工作区生命周期跨节点、后台任务多节点
- 严重失效：F1 同 executionId 两节点双跑（`register` 的 `putIfAbsent` 仅 JVM 内单飞）→ 副作用重复；F2 信号送不到；F3 事件送不到
- **关键判断**：拆 `ActiveExecutionRegistry` + `ControlSignalChannel` 是「必要但不充分」——只解决 **steering**，不解决 **admission**（防重复执行需第三个原语 `ExecutionClaimStore`）
- **重要正面事实**：框架生产代码**零 static 可变字段、零 ThreadLocal**，无隐藏全局状态 → 分布式改造是「换 bean」而非「拆单例」

**头号修复项（三方独立同结论）**：拆 `ExecutionRepository` 为 `ExecutionSnapshotStore` + `ActiveExecutionRegistry`。产品官、排障手、框架自己的 `docs/loop-topology-review.md:192` 均如此建议。

**其他已核实**：`harness-memory` 只含 `pom.xml`；`lingxi-harness-spring-boot-starter` 只有 pom+README+空 application.yaml；12 个 `@AutoConfiguration` 中仅 `McpAutoConfiguration:18` 声明了显式顺序。
