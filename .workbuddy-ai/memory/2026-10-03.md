## 前端 `order` 时序序号的存在理由（代码分析，未改代码）

- `frontend/src/services/session.ts` 只是 HTTP 客户端，**没有** `order`；真正逻辑在 `utils/session.ts#aggregateSessionMessages`、`views/chat/messageRouter.ts#getNextOrder`、`components/chat/ChatMessageItem.vue#processTimeline`。
- `order` 是**前端自造的跨集合排序键**：后端 `SessionMessageVO.records` 扁平有序，聚合时按类型分桶进 `thoughtSteps` / `toolCalls` / `aiMessages` 三个异构数组，跨类型先后关系丢失 → 用 `order` 把「记录在原始流中的位置」编码回来，供 `processTimeline` 排序还原真实执行时序。
- 两套编码：历史回放 `i*10 + 行内偏移`（+0 思考/工具结果、+1 中间文本、+2+tIdx 工具调用）；实时流 `getNextOrder = max+1` 递增追加。
- 为什么不直接渲染扁平数组：① 非 1:1（一行 AI 拆成思考+文本+N 工具；AI 行 toolCall 与 TOOL 结果行按 id 合并成一张卡）；② 渲染单位是「轮次气泡」，且要判「终结轮 = 该轮无工具调用」才定结论；③ **实时 SSE 路径压根没有扁平数组**，必须增量构建同一 `ChatMessage` 结构 —— 决定性理由；④ 分页/重载/合并要幂等（`mergeRawRecords` 按 id 去重）。
- ⚠️ 隐患（已确认，未修）：`i*10+2+tIdx` 在单行 ≥8 个工具调用时溢出撞下一行槽位；历史 ×10 与实时 +1 量纲不同，若将来同一气泡混入两者会排序失真（对应「同一轮次只允许一条 assistant 气泡」边界）。
- 设计判断（2026-10-03）：**不建议让后端改返回格式**。理由：实时路径已逼出前端增量聚合，改历史接口只换适配器输入、不消除聚合；且数据形状会从 2 个（存储扁平 + 实时事件）变成 3 个，分页（雪花游标）与「终结轮」展示语义更难收敛。更优解是**前端只改存储形态**：聚合时直接 push 一条 `ProcessTimelineItem[]`，三桶改为派生 computed，`order` 可整体删除（改动仅在 `utils/session.ts` + `ChatMessageItem.vue`）。若不动结构，至少把 `i*10+2+tIdx` 换成双字段排序键、并把「历史/实时气泡不混用」固化为断言。反例边界：若将来出现多客户端（web + mobile）各自实现聚合，才轮到后端统一格式。

## 修复：AI 过程文本被堆到过程区顶部 + 深度思考挤成一堵墙（同日）

**症状**：完成的轮次里，整轮的 AI 过程叙述被整体排在展开过程区的**最顶部**（原样显示 `**加粗**` 标记），后面才是成片的「深度思考」和工具行。

**根因（唯一）**：`utils/session.ts#aggregateSessionMessages` 里三条过程集合的 `order` **基准不同量纲**——
`aiMessages` 用「AI 文本列表内下标 `idx*10+1`」（0,1,2…→1,11,21），而 `thoughtSteps` 用 `i*10`、`toolCalls` 用 `i*10+2+tIdx`（`i` = **原始消息行**下标，实测该轮是 18,22,27…→180,220,270）。AI 文本下标增长远慢于原始行下标，于是**全部中间文本（1…131）都小于所有思考/工具（180+）**，排序后文本整体浮到顶部。用真实库数据跑生产函数复现，与用户截图逐行一致（14 文本 / 18 思考 / 25 工具）。

**修法**：`aiMessages` 改用该 AI 行自己的原始行下标（`m.rowIndex * TIMELINE_SLOT_STRIDE + 1`），与思考（+0）、工具（+2+tIdx）同基准；行内顺序天然是 思考 → 文本 → 工具。顺带把步长 10 → 命名常量 `TIMELINE_SLOT_STRIDE = 100`，收口「单行 ≥9 个并行工具调用溢出撞下一行槽位」的隐患（上面那条「未修」的隐患已修）。同时把函数头注释里过期的「最后一条非空 AI 文本作为正文」改成「终结轮次（该轮无工具调用）的文本作为正文」。

**为什么「深度思考堆叠」也是同一根因**：该轮 7 行连续 `深度思考` 是因为它们的工具调用全是 `call_sub_agent` → 被折叠成一条「团队协作」banner（钉在首个委派 order 上），本来只靠中间的**过程文本**分隔；文本被顶走后，这些 step 就连成了一堵墙。修完后每轮变成 思考 → 文本 → 工具 交替。

## 第二轮：并发双轮 → 前端两个气泡互相串事件（同日续修）

**用户补充的关键事实**：他连发了两条「继续推进」（间隔 ~30s），后端**本该拒绝**并发请求，结果两条都跑了，各出一份交付总结。

**实测后端闸门**（新会话 + curl 并发/间隔发）：
- 真·同时两条 → 第二条被拒：`{"errMsg":"该会话正在执行中"}` ✓（`SessionExecutionRegistry#beginRoot` 的进程内单飞有效）。
- 间隔 30s 发第二条（首轮仍在跑）→ 同样被拒 ✓。
- ⇒ 漏洞不在初次执行。**在恢复执行**：`ChatServiceImpl#resume` 与 `DelegationBackfillListener#resumeIfReady` 直接 `executionControl.resume(...)`，**不经过请求线程、不重新 `beginRoot`** —— 挂起时 `finishRoot` 已把单飞锁释放，而 `guardNotSuspended` 只查 `SUSPENDED`，漏掉「挂起 → 子代理回填 → 已恢复并正在跑（状态 RUNNING）」这段窗口，用户于是能开出第二个根执行。

**修法（后端）**：`guardNotSuspended` → **`guardSessionIdle`**：会话下任一执行**未终结**（`CREATED`/`RUNNING`/`SUSPENDED`，用框架 `ExecutionState#isTerminal`）就拒绝开新一轮。三处调用点（chat / chatStream / resend）随之改名。
配套（前端）：建流前被拒时，末尾是刚乐观插入的**用户**消息，旧 catch 只处理 `role==='assistant'` → 错误只进 console，用户看不见；补一条组尾错误气泡把原因写出来。

**同批修掉的两个渲染缺陷（都用真实数据/真实页面复现）**：
1. **气泡顺序随分页窗口漂移**：`aggregateSessionMessages` 原来按「该轮次的行在本次 records 里**第一次出现的先后**」push 气泡。首屏只取最新 50 条，窗口滑进某一轮中间时那一轮会晚于更晚的轮次出现 → 两个气泡上下换位（实测：同一会话 100 条页给出 `[A,B]`，应用真正用的 50 条页给出 `[B,A]`，与用户截图逐行一致）。**修法**：按轮次雪花 ID（受理先后，用 BigInt——雪花已超 `Number.MAX_SAFE_INTEGER`）排序，同轮内 `roleRank` 保证用户消息在前；缺 turnId 的旧数据回落该组首条记录 ID，解析不出数字的排最后且保持原相对序。
2. **一个轮次两条气泡**：审批恢复流给气泡钉的是本地 id（`msg-bot-resume-*`），与服务端落库行 id（`msg-<sid>-turn-<tid>`）不同源，`mergeAuthoritativeMessages` 按 id 收编拦不住；本地那条 `isComplete=false` 会被保留，服务端同一轮次的行又照常入列 → 一个轮次两个「已思考并调用」头。**修法**：`mergeAuthoritativeMessages` 里，本地仍有在途（`isComplete=false`）气泡时，服务端**同一 turnId** 的 assistant 行不再单独成条（在途正文更新鲜，卡片已取服务端权威值；收尾后自然被服务端行替换）。

## 第三轮：根会话「丢 SSE 流」——会话级流必须直接渲染根事件（同日，**推翻上一轮的补丁方案**）

**用户否掉了我上一轮的方案**（节流 + 轻量刷新），说得对：那是补丁。真问题是**根会话在请求级流结束后就没有渲染通道了**。

**机制**：请求级流（`POST /a/completion/stream` 建的那条）只服务「用户点发送的那一次」。执行一挂起（等子代理/等审批），服务端 `finally { sseEmitter.complete() }` 就把那条连接关掉。此后：
- 根执行**恢复**（`DelegationBackfillListener` 回填后 `executionControl.resume`）、子代理委派结果落地、后续轮次，**全都只在这条会话级流上**（`GET /a/completion/{sid}/events`，它一直挂着、断线自愈）。
- 而 `handleSessionStreamEvent` 当时对根事件**只做对账兜底**（`reconcileForBackgroundEvent`），不渲染 → 根气泡整轮不动，停在委派卡片上。用户的描述完全吻合：「子会话交付结果后，根会话像是没有收到，实际上另一个子 agent 却正常的在委派」。

**更糟的是那层对账自己也被饿死**：它是**重置型防抖**（每个事件 `clearTimeout` 再排 800ms），而子代理在同一会话级流里逐字推 thinking（实测 20s 抓到 1198 条 PARTIAL_THINKING），定时器被无限推迟 → 根会话一整轮一次对账都跑不了。子会话越多越活跃越严重。

**定案修法**（`views/chat/useChatView.ts`）：
- `handleSessionStreamEvent`：请求级流不在场时，**根事件直接走 `routeToSession` + `makeStreamUpsert(rootId)` 渲染**（与请求级流同一条渲染管线），不再只当触发器。子会话/映射事件仍交 `routeSessionEvent`；无 sessionId 的降级事件按归属本根会话处理。
- 对账降级为**只在终态事件**触发（`reconcileOnTerminal`）：它不再承担实时性，只是幂等自愈网（会话树 + 用量快照 + 断线/漏事件缺口）。
- 删掉上一轮加的 `utils/reconcileThrottle.ts` 与轻量刷新 `refreshLatestFromServer`（都是补丁，不再需要）。
- 双渲染仍由 `activeStreamCount > 0` 独占守卫（受控模式 `props.sessions` 不维护该计数，但 ChatView 只由路由挂载、不走受控模式）。

**对账保留规则定案（`mergeAuthoritativeMessages`）**：同一轮次**保留本地在途气泡**（`isComplete=false`，正文来自实时事件，比落库行新），服务端同一 turnId 的 assistant 行不再单独成条 —— 两条并存就是一个轮次两个「已思考并调用」头（本地 id 是审批恢复流钉的 `msg-bot-resume-*`，按 id 收编拦不住）。⚠️ 上一轮我一度改成「保留服务端那条」，那是错的：当时根事件还没实时渲染，改完根气泡直接被 DB 旧内容顶住（等于把用户的症状固化）。

**验证**：`npm test` 26/26（用例 11 顺序稳定、12 同轮不并存；12 的期望值随本轮定案改回「留在途那条」）；`vue-tsc -b --force` + `npm run build` 通过。

## 补充证据：后端确实是「一条根会话流 + 载荷自带 sessionId」（用户质疑后核实）

用户质疑「后端不会按根会话发事件」。核实结论：**会**。
- `AgentEventListener#broadcast`：`sseEventPublisher.publish(rootSessionId, payload)`，`rootSessionId = executionIdentity.rootSessionIdOfSession(sessionId)` —— 推送桶按**根会话**归档；同时 `payload.sessionId = 该执行自己的会话 id`（子执行就是子会话 id）。
- 真实抓包（订阅根会话 2106021579120050176 的流）：
  `{"executionId":"2106067648793149440","content":"改动","metaData":{"sessionId":"2106030401674936320","turnId":"2106067648801538048","parentTurnId":"2106066824704687428"},"type":"PARTIAL_THINKING","sessionId":"2106030401674936320"}`
  —— `sessionId` 是**架构师子会话**，却出现在根会话的流上。
- 所以模型就是用户说的那个：**一条常驻的根会话流，前端按 `sessionId` 分派**（子会话 → `subSessionMessagesMap[sessionId]`；根 → 根消息列表）。`handleSessionStreamEvent` 已简化成这个形状（`routeSessionEvent` 命中即返回，剩下的就是根事件 → `routeToSession`）。

仍保留的两块（都不是补丁，是契约要求的）：
- **请求级流**：`POST /a/completion/stream` 的响应本身就是一条流，是**新会话**拿到 sessionId 之前唯一的通道（会话级流要等 sessionId 才知道挂到哪个根会话）；它活着时由它渲染，结束（挂起即被服务端 complete）后交给会话级流，二者由 `activeStreamCount > 0` 独占，防追加型事件双写。
- **终态对账**：SSE 契约是「只投递挂上之后的事件、不回放」，断线/切走期间的空缺只能靠回查历史补 —— 这是自愈网，不承担实时性。

**踩坑（值得记）**：

## 精简：删掉 EnvironmentPostProcessor，数据目录降为普通 YAML 配置项（同日，取代上一节的做法）

**背景**：用户随后把 mcp / model / user_configs 的持久化整体换成了 YAML 仓储（`AbstractYamlRepository` + `YamlListStore`，文件在 `~/.lingxi/config/*.yaml`，库表退化为首次迁移来源），并明确不喜欢 EnvironmentPostProcessor。

**关键判断**：配置一旦离开库、落到文件，「循环依赖」就消失了 —— 但 `user-configs.yaml` 的根节点是**列表**，没法用 `spring.config.import` 变成 `lingxi.data.dir` 属性；而 H2 URL 必须在 DataSource 前定死。所以「数据目录来自 user-configs.yaml 的 dataStorage」这件事只能靠启动早期读文件 —— 用户选择**不做**，改为普通配置项。

**改动（净删除为主）**：
- 删：`DataStorageEnvironmentPostProcessor`、`DataStorageInitializer`、`META-INF/spring.factories`。
- `application.yaml`：新增 `lingxi.data.dir: ${user.home}/.lingxi/data`；URL 简化为 `jdbc:h2:file:${lingxi.data.dir}/lingxi;MODE=MySQL`。
- `UserConfigServiceImpl`：`@Value("${lingxi.data.dir}")` 直接回显到 VO 的 `dataStorage`。
- 删掉 `UserConfig` / `UserConfigPO` / `UserConfigRepositoryImpl` 里的 `dataStorage` 字段与 `changeDataStorage`；`init.sql` 与测试 schema 的 `data_storage` 列一并删除。
- 删掉用户为 post-processor 写的用例 `YamlRepositoriesTest#startupReadsYamlBeforeCreatingDatasource`（测的行为已不存在）。

**验证**：`mvn -o test` 342 用例 / 1 失败（既有 `SubAgentRequestFactoryTest`）。隔离冒烟（`-Duser.home` 重定向）：库落 `<user.home>/.lingxi/data/lingxi.mv.db`、`/config/current` 回显该路径；再用 `LINGXI_DATA_DIR=...` 覆盖 → 库落新目录、接口回显新值。

**踩坑（新）**：
- ⚠️ **删掉 `src/main/resources/` 下的资源后，`target/classes` 里的旧副本不会自动消失** —— 我删了 `spring.factories` 却没清 `target`，启动直接 `ClassNotFoundException: ...DataStorageEnvironmentPostProcessor`。要么 `mvn clean`，要么手动删 `target/classes/META-INF/spring.factories`。这类「删资源」的改动必须同步清 target。
- Windows 下 `user.home` 带反斜杠，拼出 `C:\Users\x/.lingxi/data` 这种混合分隔符；实测 H2 能吃，无需归一。

## 改名 + MySQL(docker) → YAML & H2 迁移（同日）

**改名**：`frontend/electron/backend.cjs` 的 `dataDir` → `userDataDir`（它其实是 Electron `app.getPath('userData')`，与 `lingxi.data.dir` 同名易误读）。main.cjs 侧改成简写 `userDataDir,`。

**迁移**：用户要求把 docker 里还在跑的旧 MySQL（`LingXi-mysql` / mysql:8.0.30 / 3306 root/root / 库 `LingXi`）的数据搬到新存储：配置表 → YAML，业务表 → H2。
- 备份：`docker exec LingXi-mysql mysqldump ... --databases LingXi > .run/migrate/mysql-LingXi-backup-20261003.sql`（118MB，54 条 INSERT）。
- 工具：`.run/migrate/Migrate.java`（一次性）。classpath = `target/classes` + `dependency:build-classpath` 产物 + `com/mysql/mysql-connector-j/9.4.0/*.jar`（驱动已不在 pom 里，但 jar 还在本地仓库）。
- 做法：业务表 14 张逐表搬运，**只取两边都有的列**（MySQL 多出的 `data_storage` 之类自动跳过）；配置表按 PO 形状走项目自己的 `YamlSerializer` 落 `~/.lingxi/config/*.yaml`（保证字段名与 App 读取一致 —— 通用行→PO 用 Jackson `convertValue`，只喂 PO 声明过的字段）。
- 结果：14 张表 **COUNT(*) 逐一一致**（合计 2917 行：session_message 1771 / tool_call 981 / session 22 / execution 52 / chat_turn 52 / agent 5 / workspace 4 / mcp 5 / model 2 / team 1 / user_configs 1）；YAML 为 1 + 2 + 5 条。
- 验证：真实 home 启动后端（18999）→ `/config/current` 读到 MySQL 那份配置（modelId=4 / LOCAL / FULL_ACCESS / DARK）、`dataStorage` 正确；`/session/list` total 14（根会话，22 行含子会话）、`/mcp/list` 5、`/model/list` 2、`/agent/list` 5。

**迁移踩坑**：
1. ⚠️ **H2 的 `getTables(null,null,"%",TABLE)` 会把 `INFORMATION_SCHEMA` 系统表一起返回** → 判「库是否为空」必须按 `TABLE_SCHEM` 过滤掉它，否则空库被误判成「已有表但缺 14 张」而拒绝执行。
2. ⚠️ **MySQL Connector/J 对 DATETIME 的 `getObject` 返回 `java.time.LocalDateTime`，不是 `Timestamp`** → 要转 `Instant` 必须补 `LocalDateTime.atZone(systemDefault())` 分支，否则 Jackson 报 `Cannot deserialize Instant from String "...T10:45:37"`（缺时区）。
3. ⚠️ **`information_schema.table_rows` 是 InnoDB 估算值，不能用来验收**（显示 session_message 1588，实际 1771）。必须 `COUNT(*)` 逐表比对。
4. ⚠️ **工具不可重复执行**：再跑一遍会重复 INSERT。要重跑就先删 `~/.lingxi/data/lingxi.mv.db`。

**遗留待用户决定**：项目内旧开发库 `D:/Code/LingXi/data/lingxi.mv.db`（10-03 当天的新数据，90KB，被 8088 上那个旧后端占着、读不到）**没有并入** **`~/.lingxi/data`。现在 App 只看 `~/.lingxi/data`（= MySQL 那份 10-02 的快照），当天的新会话不会出现在列表里。三选一：①维持现状；②把旧库文件直接挪过去覆盖（会丢 MySQL 那份）；③做真合并（agent/team/workspace 是自增主键，会撞 id，需要重映射，风险高）。**

**已解决（用户拍板①）**：服务停掉后读到这份库才发现 —— 它其实**是空的**：session / session_message / tool_call / execution / chat_turn / agent / team 全为 0，只有 1 条 workspace + 1 条默认 user_configs（94KB 全是 H2 的页分配，不代表有数据）。所以「今天的会话」本来就没落在那儿，删掉零损失。
- 已备份到 `.run/migrate/dev-h2-20261003-backup.mv.db`，再删 `data/lingxi.mv.db` + `lingxi.trace.db`（`data/` 目录留空未删）。
- 删除后重启验证：五个接口全对（session 14 根会话 / mcp 5 / model 2 / agent 5），且 `data/` 保持为空 —— 反过来证实了库文件位置确实不再随 cwd。
