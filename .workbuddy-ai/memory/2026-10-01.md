## 代码分析：execution.snapshot 反解点 / 子会话挂起传播机制（22:5x - 23:1x）

两轮纯读侧分析（未改生产代码），产出 `.run/sub-session-suspension-analysis.md`。

### execution.snapshot 反解
- **全项目唯一反解点**：`LocalExecutionRepository.java:190` 的 `objectMapper.readValue(snapshot, Execution.class)`，只存在于 `findById`。
- `findById` 先查进程内 `checkpoints`（已提交检查点缓存），未命中才 `executionMapper.selectById().getSnapshot()`。
- 所有只读场景**刻意不反解**：`findSummariesByIds` / `selectLatestBySessionAndStatus` 只 select 摘要列，排除 `snapshot`。
- 易混：`CommandApprovalExecutor.readCommandSnapshot` 的 `CommandSnapshot` 是 `tool_call.content` 的命令参数快照，**不是** `execution.snapshot`。

### 子会话挂起 → 会话不继续执行
- **核心一跳**：`CallSubAgentTool.java:222-226` —— 子执行 `SUSPENDED` → `delegationPromise()` 登记父执行 `DELEGATION` 槽位（载荷带 `subSessionId`，是回填匹配的唯一凭据）→ 父也 `promise()` → 沿委派链上传到根执行。`kind=DELEGATION` 的卡片**不是**人工审批卡，`ToolCallServiceImpl#decide` 对它直接抛错。
- **三道闸门**（都在请求线程、都在用户消息落库前）：
  1. `ChatServiceImpl#guardNotSuspended`（264-270）—— 会话任一执行 SUSPENDED 就拒开新一轮；数据源 `ExecutionMapper#selectLatestBySessionAndStatus`（`ROW_NUMBER() PARTITION BY session_id, status`）。
  2. `SessionExecutionRegistry#beginRoot`（36-46）—— 进程内单飞 + `requireNonNull`(HC-2)。
  3. `SessionExecutionRegistry#registerChild`（59-67）+ `cancelRoot`（87-97）—— `cancelled` 标志拦「停止后到达的子任务」，`CallSubAgentTool:176-178` 消费其返回值。
- **停止链路** `ChatServiceImpl#stop`（192-213）四层覆盖：会话树 + `liveChildren`（未落库的子会话）+ `activeExecutionIds` + `Thread.interrupt()`。
- **恢复**：`DelegationBackfillListener` 在子执行终态时回填槽位并 `resume(parent)`；`resumeIfReady` 两道检查（父仍有 pending 槽位不恢复 / 父已非 SUSPENDED 不恢复）是「停止 vs 审批」竞态收口。每父执行一把锁串行化并发回填；必须异步（在 `LocalExecutionRepository` 的 `synchronized` 边界外）。
- ⚠️ **发现的薄弱点**：`guardNotSuspended` 与 `ExecutionIdentity#latestSuspendedExecutionId`（67-74）**都只查单个会话**（根会话/传入会话），而委派支持多层（孙会话）。挂在孙会话上的执行**不会被新一轮准入拦下，也 `/resume` 不到**。现有 `execution.root_execution_id` 是执行归属不是会话归属，要修需按 `findSessionTree` 聚合或加 `root_session_id` 冗余列。
- ⚠️ 预留：`ChatServiceImpl#resume` 不建 SSE 流（与既有 MEMORY 记录一致）。
