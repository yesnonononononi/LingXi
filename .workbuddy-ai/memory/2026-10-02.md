## 修复：已决断卡片以未决断样子常驻页底（同一轮次两条气泡）

**症状**：答过的 Clarify 卡片仍渲染成完整作答表单，常驻会话列表底部。

**取证**：服务端全对 —— `GET /session/{id}/messages` 与 `GET /tool-call/{id}` 都返回 `pending=false / outcome=ANSWERED`；DB 该行 `completed`；探针跑 `aggregateSessionMessages`（真实接口 JSON）得到的历史聚合也正确（卡片 `pending=false`）→ **纯前端**。

**根因（三缺陷叠加）**
1. `chatSessionStore#initTurn` 在审批恢复时**复用该轮既有 assistant 气泡**并把 `isComplete` 置回 `false`；
2. `services/chat.ts#decideToolCall` 给恢复流气泡钉了**新本地 id**（`msg-bot-resume-*`），而 `useChatView#applyStreamMessage` **按 id 合并** → 找不到就 push → 多出第二条气泡（其卡片停在 `CARD_PENDING` 时刻，`pending=true`）；
3. `useChatHistory#mergeAuthoritativeMessages` **无条件保留** `isComplete === false` 的气泡 → 重复气泡每次对账都被留下，永远清不掉。

探针复现：对账后该轮次 2 条 assistant 气泡，其中一条 `CHOICE(pending=true)`。

**修复**：① `applyStreamMessage` 按 id 找不到时再按 **turnId** 归并（同轮只应一条气泡）；② `mergeAuthoritativeMessages` 对保留下来的本地气泡，若服务端同轮次已有卡片则换成服务端权威 `promptCards`。

## MySQL → H2 迁移成本实测（H2 2.3.232）

用户问成本，全部在真 H2 上跑过而不是推测：
- **完整 `init.sql` 原样灌入 `jdbc:h2:file:…;MODE=MySQL` → 14 张表全建成、零报错。** `AUTO_INCREMENT` 自增生效；**`ON UPDATE CURRENT_TIMESTAMP(3)` H2 接受且真的生效**（不需要 `MetaObjectHandler`）；`ENGINE=/CHARSET/COMMENT` 被忽略；`UNIQUE KEY`/`KEY` 索引真建出来。**不带 `MODE=MySQL` 会在 `UNIQUE KEY` 处语法错**。
- **14 个表名 + 68 个列名与 H2 2.x 保留字零冲突。**
- **唯一必须改的：6 个 `JSON` 列**（`mcp.headers/env`、`tool_call.content/raw_input/raw_output/meta_data`）——`setString` 写入后 `getString()` 读回 **`"{\"a\":1}"`（多一层引号）**，代码当字符串解析 → 载荷丢失。改 `TEXT` 即可。
- **运行时全兼容**：`FOR UPDATE` ✓；唯一键冲突 SQLState **23505** → Spring `DuplicateKeyException`，**事务未中止**（`obtainMailbox` 模式成立）✓；`LIMIT n OFFSET m` 与 `LIMIT m,n` 都 ✓。
- **要改 3 处**：init.sql 6 列改 TEXT；`MybatisPlusConfig:20` → `DbType.H2`；数据源 driver 参数化 + H2 profile。真正的成本在**回归面**（MCP 配置 + 卡片载荷两条核心链路），不在改代码。

## 数据库选型调研：换掉 MySQL 的迁移成本（为桌面端内嵌库评估）

**结论：H2 文件模式最合适**（纯 Java、无原生库、无额外进程、`FOR UPDATE` 支持、唯一键冲突是语句级回滚）。

**决定成本的关键事实（实测 grep）**
- **零 XML mapper**（`src/main` 下无任何 `.xml`）：全部走 MyBatis-Plus `BaseMapper` + LambdaQueryWrapper，生成的 SQL 基本方言无关。
- **方言只有一个硬编码点**：`MybatisPlusConfig.java:20` 的 `new PaginationInnerInterceptor(DbType.MYSQL)` → 换 `DbType.H2` 一行即可。
- **零 MySQL 专有函数**：无 `ON DUPLICATE KEY` / `IFNULL` / `GROUP_CONCAT` / `DATE_FORMAT` / `INSERT IGNORE`（4 处 "LONGTEXT" 命中全是 javadoc 注释）。MySQL 味道集中在 `init.sql` 的 DDL：`BIGINT AUTO_INCREMENT`、`DATETIME(3)`、`JSON`、`ENGINE=InnoDB CHARSET=utf8mb4`、`COMMENT`、14 处 `ON UPDATE CURRENT_TIMESTAMP`。15 张表。
- **JSON 列不依赖 DB 的 JSON 类型**：`McpRepositoryImpl` 把 `headers`/`env` 当 **JSON 字符串**存取（Java 侧解析），换 `TEXT/CLOB` 即可。
- **`FOR UPDATE` 锁定读**：`EmailRepositoryImpl:82` 的 `.last("FOR UPDATE")` —— H2/PostgreSQL 支持，**SQLite 不支持**（SQLite 无行锁，`FOR UPDATE` 直接语法错误）。
- **`DuplicateKeyException` 依赖**：仅 `EmailServiceImpl#obtainMailbox`（:188）一处，其 javadoc **自己写明**「MySQL 唯一键冲突不中止事务，不像 PostgreSQL 会把事务置为 aborted」→ **PostgreSQL 与该模式天然冲突**（需改 `ON CONFLICT DO NOTHING` 或加 savepoint）。
- **`LIMIT` 出现在 4 处 `.last("LIMIT n")`**（ExecutionIdentity:72、ExecutionRepositoryImpl:52、McpRepositoryImpl:63、SessionMessageRepositoryImpl:48）—— H2/PostgreSQL/SQLite 都支持。
- **主键策略**：`IdType.AUTO`（DB 自增）用于 mcp/model_config/workspace/session/agent/team/execution；`IdType.INPUT`（雪花，`IdUtil.getSnowflakeNextId()`）用于 session_message/session_context/email。换库要按方言写自增语法。
- **`update_time` 双写**：`init.sql` 14 处 `ON UPDATE CURRENT_TIMESTAMP`，但代码里也有 8 处显式 `.updateTime(...)`。**H2/SQLite/PostgreSQL 都不支持 `ON UPDATE CURRENT_TIMESTAMP`** → 建议补一个 `MetaObjectHandler`（当前项目**没有**）。
- **H2 已有先例**：`src/test/resources/{tool-call,email,chat-turn,execution-status}-schema.sql` 是手改的 H2 镜像（`CLOB`/`TIMESTAMP`），`email-schema.sql:16` 已建 `uk_email_workflow_recipient` 唯一索引，邮件链路测试在 H2 上跑通 → H2 兼容性已被项目自己验证过一部分。

**顺带发现**：`docker-compose.yml` 里有 `redis:8` 服务，但 `pom.xml` **没有**任何 redis 依赖、`src/main` 里 `redis` 只出现在 javadoc 比喻里 → Redis 容器是死配置，可删。

**若采纳 H2**：`<scope>test</scope>` 去掉 + `DbType.H2` + `init.sql` 出一份 H2 版 DDL（三处同步规则里再加一处）+ `MetaObjectHandler`；JDBC URL 用 `jdbc:h2:file:<userData>/data/lingxi;MODE=MySQL;DATABASE_TO_LOWER=TRUE`。注意 H2 2.x 保留字（`VALUE`/`KEY`/`USER`/`YEAR` 等）可能需 `NON_KEYWORDS`，`session` 表名待实测。

## 前端：SubAgent 协同条文字被挤成竖排 + 撑破卡片（2026-10-02 晚修）

- **症状**：`ChatMessageItem.vue` 的 `item.type === 'sub_agent'` 协同条，7 个成员时左侧「团队协作」+「N 成员正在协作」被压成**逐字竖排**，且成员按钮条溢出圆角卡片右边界（Agent #7 被卡片外沿切掉）。
- **根因（两个 class 互相咬）**：外层 `flex ... justify-between gap-3`；左块 `min-w-0`（允许被压到 0 宽 → 中文逐字换行）；右成员条 `shrink-0 overflow-x-auto`（`shrink-0` 让它按 max-content 撑开，宽度不受约束 → `overflow-x-auto` **永不生效**，直接溢出父级）。
- **修法**：左块 `min-w-0` → `shrink-0`，两个文案加 `whitespace-nowrap`；成员条去掉 `shrink-0`、补 `min-w-0`（`overflow` 非 visible 时自动最小尺寸为 0，滚动容器才成立），成员按钮各自 `shrink-0` 防压扁。外层保留 `justify-between` 以便成员少时仍右对齐。
- ⚠️ **别被截图里的「文字重影」骗了**：用户截图是 1333px 宽被前端缩到 1066px 显示，降采样产生伪重影。放大 3 倍看原图（`.run/tools/png_crop.py`，纯 zlib 手写 PNG 解码/裁剪/放大，本机 pip 无网络装不了 Pillow）确认正文渲染是干净的。**判断「叠加/重影」类问题必须先放大原图**。
