## 改造：ExecutionResumeCoordinator 的指数退避换成框架 RetryUtil

**决策**：用户明确选择「字面换成线程内重试」，接受代价（退避不再落库、`attempts` 不再计重试次数、`dispatching` 门闩在整个退避期间被占）。我事先把三条代价和「崩溃不再丢意图（启动分流能救）」都摆出来了，用户确认后才动手。

**关键设计点（后人改动前必读）**：重试单元**必须**是「重读检查点 → 判闸门 → resume」整体（`attemptResume`），不能只包 `resumer.resume`。依据：框架 `DefaultExecutionController.resume` 只校验**内存对象**的状态（`Only a suspended execution can be resumed`），不查库；重试若跳过快照校验，迟到的恢复会作用在 stop/另一条决策已改过的执行上。且**确定性结论（已终态/已运行/仍有槽位/缺会话归属）一律返回枚举、绝不抛出** —— `RetryUtil` 对任何 Exception 都会重试，抛出去等于把「让位」也重试一遍。

**参数**：`RetryUtil.retry(2000L, MAX_ATTEMPTS-1=2, 2, MILLISECONDS, ...)` → 3 次尝试；退避是 `random(0, 2000*2^n)` 的**随机抖动**（不是确定性 2s/4s/8s）。`requeueWaiting` 的 2s 是轮询等待、不是失败退避，保留落库 `deferTo`，常量改名 `REQUEUE_DELAY_MILLIS`。

**框架侧**：`RetryUtil` 在 `dev-framework-ddd-helper` 的 `1.0.5`（本地 16:01 重建，含 5/6/7 参三个重载，7 参带 `maxDelay` + `exceptionPredicate`）。**`1.0.5-SNAPSHOT` jar 里没有 RetryUtil**（那是 10-03 的旧包）→ `pom.xml` 的 `<ddd-starter>` 由 `1.0.5-SNAPSHOT` 改为 `1.0.5`。⚠️ 1.0.5 的 `.asc` 签名是 10-03 的，今天的本地 jar 覆盖了它；若 1.0.5 曾发布到远端，其他机器/CI 会解析到不含 RetryUtil 的旧 1.0.5 → 建议框架发 1.0.6 再 pin。

**我复核时发现并修掉的回归**：`catch (Exception)` 会把 `RetryUtil` 抛出的 `InterruptedException` 一并吞成 `markExhausted` —— 而中断来自关闭（`close → shutdownNow`），此时执行仍是挂起态、意图完全可恢复，落 EXHAUSTED 会把「本可自动恢复」永久降级成「只能人工触发」。修法：在泛 catch 之前单列 `catch (InterruptedException)`，重新置位中断标志且**不写终态**，把行留在 CLAIMED 交给启动分流。守卫 `interruptDuringBackoffDoesNotWriteTerminalState`（变异证明：删掉该 catch → 断言红，`实际=StateWritten[state=EXHAUSTED, errorReason=java.lang.InterruptedException]`）。同时删掉因本次改造而死的 `ExecutionResumeTask.exhausted(int)`（全仓零调用）。**误删后已回滚**：我一度把 `fail(String, Instant)` 收成单参，编译暴露 `ExecutionResumeTaskRepositoryTest` 仍在用 —— 我的 grep 用了 `fail(.*retryAt`，匹配不到 `fail(..., null)`，属典型假阴性。教训见 MEMORY.md 工程教训。

**验证**：`mvn -o test -Dtest='ExecutionResumeCoordinatorTest,ExecutionStartupReaperTest,ExecutionResumeTaskRepositoryTest'` → 33 tests / 0 fail / BUILD SUCCESS；`ExecutionResumeCoordinatorTest` 连跑 3 次均 12/12 绿。⚠️ 变异态下有一次 `await(firstAttempt)` 20s 超时（失败点与变异无关，变异在其下游），未能归因，属该测试的残留抖动风险。

**未修（上报用户）**：`markFailed(task, "执行缺少会话归属")` → `fail(reason, null)` → 落 `FAILED + nextAttemptAt=NULL`，而 `listDispatchable` 的条件是 `state IN (READY, FAILED) AND (next_attempt_at IS NULL OR <= now)` → **立即可派发**；`purgeFinishedBefore` 只清 SUCCEEDED/SUPERSEDED → 该行永不被清，于是巡检每 5s 重投一次、永远失败。这是**改造前就存在**的缺陷，`exhaustRetries` 的 javadoc 恰好警告过这个模式。建议改走 `flagForManual`（NEEDS_MANUAL）。



## 重构：恢复语义改为「只尝试一次」+ 最小持久请求标记

**用户批准的契约**：批准 = 「决策已落库，后端只尝试恢复一次」；启动失败即收口 FAILED；不重试、不退避、不轮询。但保留最小持久请求标记，用于重启后区分「正常等审批的 SUSPENDED」与「已批准但恢复没起步的 SUSPENDED」。状态默认 FAILED，只有显式取消才 CANCELLED。

**三个落点（都复用既有机制，无新抽象）**：
1. **竞争失败判据 = `ExecutionActivity.isActive()`**（`LocalExecutionRepository:280`，背后是框架控制槽位表）。不用匹配框架的 `"execution is already running"` 文案。
2. **运行阶段边界 = 落库状态是否离开 SUSPENDED**。框架 `RuntimeProcessorTemplate.process` 顺序是 `save` → `resumeChecked()+save`（落 RUNNING）→ 才进 loop，**状态先落库**。异常后重读：终态/非 SUSPENDED/代际变/isActive → 框架已接管 → 让位。这就是「loop 已跑完、回写上下文抛异常不得改判失败」的护栏。
3. **失败收尾 = `ExecutionControl.fail(execution, cause).run()`**，一条链完成「落终态+结束时间 → 仓储提交后通知轮次收口+清理未决工具 → 发布终态事件」。业务侧不要手写轮次收口（会与框架打架）。先例 `PreparedChatExecutor#markStartupFailedQuietly`。
   ⚠️ **但我给实现方的守卫抄错了**：`markStartupFailedQuietly` 的「SUSPENDED 一律跳过」是它那个场景的口径；本场景要求「仍 SUSPENDED ∧ ¬isActive ⇒ 收口 FAILED」，若照抄该守卫这一支永远收不了口（req-4 不可达）。实现方顶回来了，我核实 `Execution#failChecked` = `requireNotTerminal()`（只拦终态）→ **SUSPENDED→FAILED 合法**，他们的判断对。教训：跨场景抄守卫要先核对那个守卫在**本**场景是否仍成立。

**顺序保证**：`H2SchemaInitializer` 是 `ApplicationRunner` + `HIGHEST_PRECEDENCE`，早于 `ExecutionStartupReaper`（`ApplicationReadyEvent`）—— 重建先发生，收尸钩子看到的是空表，不会误收口。

## 排查：每轮/每次断连刷 `流连接异常` WARN（中文「你的主机中的软件中止了一个已建立的连接」）

**症状**：`SseEventPublisher:97-100` 的 `onError` 回调反复打 WARN，伴随 `结束流连接`。

**已证机制（读 Spring 6.2.11 源码确认，非推测）**：该 WARN **只**由容器异步错误路径触发 —— Tomcat 探测到客户端断开 → `AsyncListener.onError` → `WebAsyncManager` 的 `addErrorHandler` → `DeferredResultInterceptorChain.triggerAfterError` → `DeferredResult.LifecycleInterceptor.handleError` → `errorCallback.accept(t)`，而 `errorCallback` 正是 `emitter.onError(cb)` 注册的那个。**不是**我们自己的 `send` 失败：`completeWithError(e)` 走 `setErrorResult` → `setResultInternal`，不回调 errorCallback。

**为何日志里是中文原文**：`DisconnectedClientHelper.EXCEPTION_PHRASES` 只含英文 `"broken pipe"` / `"connection reset by peer"`；Windows + JDK 中文 locale 给的是「你的主机中的软件中止了一个已建立的连接。」→ 不匹配 → 不包装成 `AsyncRequestNotUsableException` → 原始消息直达 `onError`。Spring 的设计本意就是这类异常只打一行 DEBUG。

**服务端不关流（已 grep 确认）**：`SseEventPublisher` 的调用方只有 `connect`（ChatServiceImpl#subscribeSession / ToolCallDecisionService / ToolCallServiceImpl）与 `publish`（AgentEventListener），**没有任何业务路径对会话级流调 `finish`/`complete`**。所以断连一定是客户端侧。

**顺带发现两处前端缺陷（未修，已写进 MEMORY.md §三）**：
1. `useChatView#ensureSubscribed` 每次发送都 `acquire(rootId)`，而 `release` 只在 rootId 变化时调用 → **refCount 只增不减**，切走会话时永远释放不掉，旧连接长期滞留。
2. `sessionEventStream#currentRootId()` 返回 Map 中**最后插入**的键，不是被请求会话的键 → `waitUntilReady` 可能等错连接，5s 超时后 `submitCommand` 触发 `reconnectStream()` → `reconnect()` abort 全部连接再重开。

**待确认（需客户端日志）**：`release()`（refCount→0）/ 页面卸载 / `reconnect()` 三者中哪一个实际触发了本次断连。建议诊断：把 `logging.level.com.summit.dp.shared.event` 开到 DEBUG —— 若 WARN 前有 `流事件发送失败，摘除该流` 则属 send 失败路径，否则纯属容器探测到的客户端断连；再对照前端控制台 `[SessionEventStream]` 输出。

## 修复：会话级流生命周期两处缺陷（refCount 泄漏 + 连接查找歧义）

**缺陷 1（refCount 只增不减）**：`useChatView#ensureSubscribed` 每次发送都 `acquire(rootId)`，而 `release` 只在 rootId 变化时调 → 发 N 次后计数 = N+1，切走会话时归不了零，旧连接永远滞留（后端 `total` 只增）。

**缺陷 2（连接查找歧义）**：`sessionEventStream#currentRootId()` 返回 Map 里**最后插入**的键，不是被请求会话的键 → 多会话并存时 `waitUntilReady` 会等到别的会话上 → 误判超时 → `submitCommand` 触发 `reconnectStream()` → `reconnect()` abort 全部连接（正是「每次断连刷 WARN」的放大器）。

**改法**：
- `sessionEventStream.ts`：新增 **`ensure(rootSessionId)`**（确保有活跃连接、**不计数**；无任何连接时按 `acquire` 记账，避免造「有连接、无使用者」的孤儿）；抽出私有 **`revive(connection)`**（`acquire` 与 `ensure` 共用「断则补挂」）；**删除 `currentRootId()` 与 `resolveCurrentConnection()`**，改为私有 `resolveConnection(rootSessionId)`；`waitUntilReady` / `isReady` / `getHealthState` 全部改为**显式传根会话 id**（多会话并存时没有「当前连接」这个概念）。
- `useChatView.ts#ensureSubscribed`：`acquire` → `ensure`，`waitUntilReady(timeout)` → `waitUntilReady(rootId, timeout)`。

**守卫（均已做变异证明）**：
- `singleSessionStream.test.ts#1d`：连发 3 次后 `resolveRefCount(ROOT)` 必须仍为 1，且 `release` 后 `isConnected()===false`。变异（`ensure` 改回 `acquire`）→ 红：`实际=4`，expected 1，仅此 1 条失败（21 pass / 1 fail）。
- `singleSessionStream.test.ts#1e`：两个根会话并存（A 已握手、B 未握手，B 后插入）。`waitUntilReady(A)` 必须**立即**成功（改成 `await` 会在变异态下挂住，故用「5 tick 后断言 resolved===true」保证变异是**红断言**而非超时）；`waitUntilReady(B,100)` 必须超时失败。变异（改回「最后插入」）→ 红：`expected: true, actual: ~`，仅此 1 条失败（21 pass / 1 fail）。
- 既有调用点同步改签名：`singleSessionStream.test.ts`（waitUntilReady×2、isReady×4、getHealthState×4）、`cardReadinessAndSessionStream.test.ts:192`。

**验证**：全量 `npx tsx --test` 13 个文件 → 92 tests / 88 pass / 4 fail，4 条全部是既有 `reasoningEffort.test.ts`（已 grep 标题确认）；`CODEBUDDY_SAFE_DELETE_ENABLED=0 npm run build` → `✓ built in 1m 9s`，`vue-tsc -b` 无报错。**未提交**。

| 累加点 | `DefaultConversationManager.addMessage:108` → `TokenUsageEntity.add()`（注释：*Accumulates ... across model turns*）→ 终态事件 `TokenInfo.from(execution.getTokenUsage())` → `chat_turn` | `ContextUsageReporter`（`AgentLoopStepRunner:279` 每 `usage-report-interval` 轮 + `RuntimeProcessorTemplate:118` 收尾各发一次）→ `ContextUpdateEvent` |
| 含什么 | 每次的 prompt + **工具 schema** + 输出 + 思考 | 只有消息列表（system/user/ai/tool），**不含工具 schema** |

**换算关系：用量 ≈ 模型调用次数 × 平均上下文。**

**用真数据验证**（会话 `2107843417412362240`「你有什么skill」，走 HTTP API 取的）：
- 该轮 `input=99924 / output=3822 / total=103746`（= 截图 103.7K），会话 `contextTokenCount=15473`（= 15.5K）。
- 该轮含 **7 条 AI 消息**（6 次工具调用 + 1 次收尾正文）→ **模型调用 7 次**。
- `99924 / 7 = 14275` ≈ 最终上下文 `15473` —— 完全吻合「每次循环都把当时的整段上下文重发一遍」。**没有重复累加**（若双计应为 ~210K）。

**两个「看着像 bug 其实不是」的点**：① 上下文数**天然偏小** —— 不含每次请求都发出去的工具 schema（MCP 工具尤其大）；要精确需框架侧把 tool definitions 计入 `count()`。② 跑的过程中**会滞后** —— `usage-report-interval: 5`（`modelExecutions % 5 == 0` 才上报），只有收尾那次准；长轮次中途看偏小。

**★ 排查技巧（可复用）**：`~/.lingxi/data/lingxi.mv.db` 被运行中的后端独占（JDBC URL 无 `AUTO_SERVER`），直接 `org.h2.tools.RunScript` 会报 `The file is locked`。**改走 HTTP API**：`GET http://localhost:8088/session/list`（拿会话与 `contextTokenCount`/`contextMaxTokens`/`contextRatio`）、`GET http://localhost:8088/session/{id}/messages`（拿 `turns`，每轮 `inputTokens`/`outputTokens`/`totalTokens`）。注意 `SessionController` 是 `/session`（无 `/a` 前缀），而 `ChatController` 是 `/a`。⚠️ 用 Windows 版 python 解析时路径要写 `D:/...`，`/tmp/...` 它看不见。

## 修复：团队描述上限 500 → 1000（三处不一致导致「在 DB 列宽上炸」）

**真实断点不在你以为的地方**：用户说「最多 500 字」，但后端 `Team.MAX_DESCRIPTION_LENGTH` **本来就是 1000**，`TeamValidator` 也按 1000 放行。真正的 500 有两处：

2. `init.sql` 的 `team.description VARCHAR(500)`。

于是链路是「前端先拦在 500 → 拦不住时后端放行 → 最后 H2 在列宽上抛 `Value too long`」。**这不是简单改个数字**：只把前端放开到 1000 会让用户直接撞上 DB 报错。

**改动**：
- `useTeamsTab.ts`：新增模块级常量 `TEAM_DESCRIPTION_MAX_LENGTH = 1000` 并替换字面量（附「三处必须同步」注释）。
- `init.sql`：`team.description` → `VARCHAR(1000)`。
- 新增 `db/migration/V4_team_description.sql`（`ALTER TABLE team ALTER COLUMN description VARCHAR(1000)`）+ `V4_record.sql`。
- `H2SchemaInitializer`：新增 `migrateV4` 与 `columnSize(...)`。

**★ 关键发现：`H2SchemaInitializer` 此前没有「加宽已有列」的能力。** 既有迁移只认「缺表 / 缺列 / 缺索引」（`hasColumn` / `hasIndexNamed`），而**加宽列不是缺列**，且 `init.sql` 里改列宽对已有库**完全无效**（`CREATE TABLE IF NOT EXISTS` 不改已存在列）。所以必须按 `COLUMN_SIZE` 判定后显式 ALTER。`migrateV4` 先 `hasColumn` 再比宽度：列整个缺失时不介入（ALTER 会失败，那属于建列的事），保持「只补自己那一项」的边界；只认「低于目标宽度」，对已是 1000 的库天然幂等。

**实测 H2 语法**：`ALTER TABLE t ALTER COLUMN c VARCHAR(n)` 在 H2 2.3.232 + `MODE=MySQL` 下有效（用 `org.h2.tools.Shell` 查 `INFORMATION_SCHEMA.COLUMNS.CHARACTER_MAXIMUM_LENGTH` 确认 500→1000 真的生效；注意 H2 2.x 的 `INFORMATION_SCHEMA.COLUMNS` **没有** `COLUMN_SIZE` 列，那是 JDBC 元数据里的名字，写 SQL 要用 `CHARACTER_MAXIMUM_LENGTH`）。

**守卫**：`H2SchemaMigrationTest#legacyNarrowTeamDescriptionColumnIsWidened` + fixture `src/test/resources/team-legacy-schema.sql`（旧列宽 500 + 一行数据）。含金丝雀断言（先证明列宽扫描器能读到 500，否则「500」可能是「扫不到→恒返回 0」的假绿），并断言加宽不丢数据、二次启动幂等。**变异证明**：把 `migrateV4` 的条件改成 `false && ...` → 红：`init.sql 改列宽对已有库无效，必须由迁移显式 ALTER 加宽 ==> expected: <1000> but was: <500>`，仅此 1 条失败（3 tests / 1 fail）。
