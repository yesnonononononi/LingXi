# 2026-09-29 工作日志

## 协作工具端到端修复：call_sub_agent / send_mail_to_agent

**用户报障**：真实运行里两个工具都失败 —— `send_mail_to_agent` 返回「当前执行未绑定 Agent，无法发信」、`call_sub_agent` 返回「未确定当前协作团队，无法委派任务」。

**根因（从本地 MySQL 实际数据核实，不是推测）**：
- `execution` 表最近 6 条快照的 `agentRequest.runtimeParameters.attributes` **只有** `lingxi.session_id / workspace_id / model_config_id / agent.access.mode / command.approval.policy` —— **既没有 `lingxi.agent_id` 也没有 `lingxi.team_id`**。
- `session` 表最近 6 条会话 `team_id` 全是 `null`（用户是在**裸模型档位**下聊的）。
- 但 `RequestPreparer.toolListOf` 在「未配工具清单 + 可写档位」时返回 `null` = **不加限制 = 全部已注册工具**，于是模型拿到了这两个协作工具，一调用必然失败。
- 即：**不是工具坏了，是模型被给了它用不了的能力**。

**修复**：
1. `RequestPreparer.toolListOf` 新增 `withoutUnusableCollaborationTools`：把注册表展开成显式清单后按身份收口 —— `call_sub_agent` 需 `TEAM_ID`、`send_mail_to_agent` 需 `AGENT_ID`，不满足即从模型可见清单剔除（含显式清单路径）。注册表为空时仍返回 `null`，避免把工具集清空。
2. `AgentWorkflowOrchestratorImpl.commanderTools` 在授予 `call_sub_agent` 的同时一并授予 `send_mail_to_agent` —— 此前**没有任何 Agent 配置**写它，团队里没人发得出信，工具形同虚设。

**本地库迁移（已执行）**：`email` / `email_message` 从旧结构（`agent_id/root_execution_id/target_execution_id`）切到新结构（`workflow_execution_id/recipient_agent_id` + `uk_email_workflow_recipient`）。迁移前两表均 **0 行**，脚本带「有数据即 ABORT」的安全闸。

**端到端验证（真实起服务 + 真实 DeepSeek 模型 + 真实 MySQL）**：
- 团队会话（`teamId=3` 软件开发组，指挥者=产品经理 agent 5，`workspaceId=4`）：
  - `send_mail_to_agent(toAgentId=6)` → `Email sent successfully`
  - `call_sub_agent(agentId=6)` → 子 Agent 架构师真实执行并回 `ok`，SSE 出现 `SUB_AGENT_SESSION_CREATED`
  - DB 落库：`email(wf=2104605511034044416, recipient_agent_id=6, team_id=3)`、`email_message(sender_id=5, content=…, status=CONSUMED)` —— **已被子 Agent 的拦截器消费**，角色邮箱闭环成立
- 裸模型会话（无 teamId / 无 agentId）：模型自报工具清单为 `compact_context, execute_command, edit_file, web_search, require_choice, read_file, create_plan` —— **两个协作工具都不在其中**，模型明确回答「这两个工具不可用」。

**新增测试**：`CollaborationToolExposureTest`（5 例）——裸模型两者都不暴露、单 Agent 保留发信剔除委派、团队指挥者两者都保留、显式清单同样收口、注册表为空保持旧语义。全量 **155 通过 / 0 失败**。

## 追加：团队成员（子执行）获得 TEAM_ID + send_mail_to_agent + 成员话术

**用户要求**：团员要给 `teamId` 和 `send_mail_to_agent`，但**不给** `call_sub_agent`；另外给它们额外提示词，告诉它们团队成员（与 commander 同一份话术）。

**改动**：
- 新增 `TeamPromptComposer`（`agent.infrastructure.workflow`，静态工具类）：`commanderPrompt` / `memberPrompt` / `roster`。**指挥者与成员共用同一个 `roster` 渲染**（同一 `- id: … | name: … | description: …` 格式、同样的空名单占位），差别只在职责段：指挥者可委派，成员明确「没有委派能力、需要同步时用 send_mail_to_agent」。`AgentWorkflowOrchestratorImpl.polishPrompt`/`describeAgent` 已删除，改调 composer（指挥者输出保持逐字一致）。
- `CallSubAgentTool`：新增 `childAttributes`（把父执行的 `TEAM_ID` 随委派下行）、`memberTools`（剔除 `call_sub_agent`、补 `send_mail_to_agent`；未配清单时也至少给发信）、`buildSubAgentPrompt(agent, team, callerPrompt)`（嵌入成员话术 + 名单）。`delegatedTools` 已改名 `memberTools`。
- **重要副作用**：子执行拿到 `TEAM_ID` 后，「靠属性缺失阻止二次委派」这层保险消失，真正的守卫只剩 `memberTools` 把 `call_sub_agent` 从子执行清单剔除。相关注释与 `MailSendContext` javadoc 已同步更正。
- 新增测试：`TeamPromptComposerTest`（4）+ `CallSubAgentMemberWiringTest`（3）。全量 **162 通过 / 0 失败**。
