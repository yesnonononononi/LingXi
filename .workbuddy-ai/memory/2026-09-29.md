## search_tool 迁入框架 + MCP 工具渐进式披露

**用户要求**：`search_tool` 移到框架侧 `D:\code\starter\lingxi-harness-agent`；MCP 工具**不随静态工具一起**进 `ModelRequestFactory`；MCP 工具以 `McpResume` 形式做渐进式披露（`SystemPromptAssembler.withMcpToolPrompt`）。

**定案的机制（三层披露）**：
1. **第 0 层（提示词）**：`McpToolScope.resumes()` 把**全部**已发现 MCP 工具的 name+description 写进系统提示 `## MCP Tools` 段，并说明「调 `search_tool` 取 schema，取到后下一轮可调」。schema 绝不进提示词。
2. **第 1 层（检索即披露）**：`SearchToolExecutor` 命中后调 `scope.disclose(命中的名字)`。账本 `disclosed` 挂在 `McpToolScope` 上 —— 它本就同时被 `ToolExecution`（写）与 `ModelRequestFactory`（读）持有，零新管道、不跨请求泄漏、`close()` 一并释放。`disclose` 只认 scope 真正持有的名字，所以静态工具名传进去自动落地，调用方无需区分来源。
3. **第 2 层（下一轮进 tools 数组）**：`ModelRequestFactory.availableTools` 不再并集整个 scope，只并集 `disclosedTools()`；过滤条件 `allowedFor(whitelist) || isDisclosed(name)`。
- **准入不动**：`DefaultToolExecutionManager.admissible` 保持「scope 内一律放行」。两个闸门**故意不一致**：一个决定「给模型看什么」，一个决定「调用能到哪」。所以模型若在检索同一批里直接调该工具也能成功。

**关键约束（决定了为什么必须做账本）**：`ChatRequestBuilder` 把工具转成真正的 `ToolSpecification` 下发，标准函数调用下模型**只能**为已声明的工具产生结构化 `tool_calls`。所以「永不进 tools 数组」的纯提示方案会让 MCP 工具彻底调不动。

**改动清单**：
- 框架：`McpToolScope`（账本 + `disclose`/`isDisclosed`/`disclosedTools`/`resumes`）、`McpResume`（补 javadoc）、`harness-runtime/tool/SearchToolExecutor`（新建，从应用侧迁入；`Supplier<ToolRegistry>` 而非 Spring `ObjectProvider`，因 harness-runtime 无 Spring）、`ModelRequestFactory`、`SystemPromptAssembler`、`ConversationManager.startConversation` 加 `McpToolScope` 形参、`RuntimeProcessorTemplate`、`SearchToolProperties` + `SearchToolAutoConfiguration`（`matchIfMissing=true` + `@ConditionalOnMissingBean(name="searchToolDefinition")` 留替换口）。
- 应用：删 `dp.tools.baseTools.search.SearchToolExecutor` / `SearchToolArgument` / `CommonToolConfiguration.searchToolDefinition` / 应用侧测试；`ToolCatalog.SEARCH_TOOL = SearchToolExecutor.NAME`（单一来源）；`application.yaml` 加 `search-tool.enabled`。**保留** `RequestPreparer` 的 MCP 兜底授予 —— 框架 `AgentRequest.toolList` javadoc 明确「应用对模型可见能力保留最终权力」，所以「默认可见」由应用兜底实现，框架不擅自放行静态工具。

**顺手修掉的两个既有缺陷（都在本次改动路径上）**：
1. `SystemPromptAssembler.withTaskPrompt(null)` **NPE**。`RequestPreparer.buildRequest` 从不设 `task`（只有 `CallSubAgentTool` 设），所以**每个根执行都在 `startConversation` 崩**。基线 `LoopRegressionTest` 有 8 个用例因此失败（此前 MEMORY 里「61 通过/1 失败」的记录是**过时的**）。现已加空值守卫。

## 修「每轮 execution 都刷 SSE WARN」

**用户报障**：每轮执行都出现 `SseEventPublisher: Failed to send SSE event` + `AsyncRequestNotUsableException` / `ClientAbortException`（"你的主机中的软件中止了一个已建立的连接"）。用户猜测是 MCP 请求级关闭导致的。

**实为误判，堆栈里没有任何 MCP 帧**。真实链路（堆栈逐帧对过）：
```
RuntimeProcessorTemplate.clear(:103)            ← finally 里的收尾
  → ContextUsageReporter.publish(:37) → publish(:42)
    → RuntimeEventPublisher.onContextUpdate
      → AgentEventListener.onContextUpdate → broadcast → sseEventPublisher.publish → send → emitter.send
```
**根因**：`RuntimeProcessorTemplate` 先发终态事件（`onComplete`/`onCancel`/`onError`，第 58/62/75 行），前端收到终态就关流；**之后** `finally` 的 `clear()` 才做收尾用量推送。所以最后那条推送必然写到已断开的流上 —— **每轮都发生，是确定性行为**。且 `AsyncRequestNotUsableException` **继承 `IOException`**，被 `catch (IOException | IllegalStateException)` 当成故障打成 WARN + 完整堆栈。

**修复**（只动应用侧传输层，框架零改动）：
- `SseEventPublisher.send` 写失败 → `log.debug`（只打最内层 cause 的类名+消息，不再打堆栈），并**主动把该 emitter 从注册表摘掉**（客户端断开后容器未必立刻回调 `onError`，留着只会每轮重试）。
- 把原先嵌在 `connect` 里的移除 lambda 抽成 `remove(rootSessionId, emitter)` 复用（幂等、空桶回收语义不变）。
- 新增 2 个用例：写失败被摘掉且不重复写、一条流失败不影响同会话其他流。`SseEventPublisherTest` **5 通过 / 0 失败**。

**没做的事**：没有去掉 `clear()` 里的收尾用量推送——挂起（SUSPENDED）路径走同一个 `clear()`，那时前端流还开着，这条推送是有用的。

**用户报障**：前端切会话再切回来就丢失 SSE 流，只能靠查 DB 历史来确定。问「前端用 pinia 管理全局事件流能解决吗」。

**根因（两个，都不是前端能修的）**：
1. **没有会话级订阅入口**：全仓库只有 `chatStream` / 命令审批 / tool-call 决策三处建流，且 `chatStream` 在执行结束时 `emitter.complete()`。切回来时那条流已经不存在了。
2. **无人订阅时 `publish` 静默丢弃** → 离开期间的事件永久消失；库里只有已完成轮次，正在生成的那一轮补不回来。
   顺带发现 **`resume` 根本不建流**（只恢复执行并返回消息），所以恢复后整轮事件没有任何订阅者。

**实现**（应用侧，框架零改动）：
- `SseEventPublisher` 重写：每会话一个 `Channel`（回放日志 `ArrayDeque` 上限 200 + 订阅者列表，全部由通道监视器保护）。每条事件分配单调递增序号，作为 SSE `id` 下发。
- `connect(rootSessionId, lastEventId)`：登记订阅 → 回放缺口 → 放行积压。**订阅先以「回放中」状态登记**，期间事件进 `queued` 不直发，避免新事件插到更旧的回放前面。
- 缺口补不上 → 先发 `event: gap` 帧（`id` 取当前最旧序号），前端据此回查历史。
- 无人订阅不再丢弃：事件照样进日志；通道在最后一个订阅者离开后保留到 TTL 30 min，心跳顺带清扫。
- `ChatService.subscribeSession(sessionId, lastEventId)` + `GET /a/completion/{sessionId}/events`，`lastEventId` 支持查询参数与 `Last-Event-ID` 头。

**测试**：`SseEventPublisherTest` **8 通过 / 0 失败**（新增：切走期间事件在切回时补发且之后实时继续、首次挂载不回放、缺口补不上先发 gap 帧）。

**踩坑（测试写法）**：Spring 把 SSE 帧拼成**一段多行数据项** `"id:101\nevent:gap\ndata:"`，不是按 `id`/`event`/`data` 分开的多个数据项；而且 `DataWithMediaType` **没有重写 `toString()`**。所以断言必须 `build().stream().map(part -> String.valueOf(part.getData())).collect(joining("\n"))` 再找子串。另：`SseEmitter.send` 抛受检 `IOException`，调用它的测试方法必须 `throws`。

## 改向：去掉回放/gap，改由前端回查历史 + 引入 pinia SSE 路由中心

**用户决定**：回放与 gap 不要了，缺口由前端查 session 接口对齐；改为给前端引入 pinia 的 SSE 路由管理中心。

**服务端（简化，已删回放那套）**：`SseEventPublisher` 回到「`rootSessionId → Set<SseEmitter>` + 心跳」的简单扇出，删掉序号、回放日志、缺口帧、catching-up 积压队列、通道 TTL 清扫。保留两件：会话级订阅入口 `GET /a/completion/{sessionId}/events`（去掉 `lastEventId` 参数与 `Last-Event-ID` 头），以及写失败降级 DEBUG + 摘除 emitter 的修复。`SseEventPublisherTest` 回到 5 例（保留两条断开相关）。后端 `compile` 通过。

**前端（新增）**：
- 装 `pinia`（原先 `node_modules` 里没有），`main.ts` 里 `app.use(createPinia())`（**先于 router**）。
- `src/stores/sseRouter.ts`：连接归属收上来按根会话保管；**订阅表与连接表分开**（连接断了不丢订阅）；`openStream` 同会话复用连接；`finish` 只摘自己那条连接；`onReattached` 在「连接已在跑且已投递过事件」时回调，提示消费方回查历史；`AbortController`/订阅者集合不放 reactive，只用 `statuses` 暴露状态。
- `utils/sse.ts` 的 `readSseResponse` 加 `stopOnTerminal`（缺省 true），会话级订阅传 false —— 否则第一次执行结束订阅就静默失效。

**验证**：`npm run build`（含 `vue-tsc -b`）通过，856 modules transformed；后端 compile 通过。

**关键发现（迁移点）**：`useChatView.ts` **主动在切换会话时 abort 流**（686-689）与卸载时 abort（1324-1326），发送路径在 615-660 —— 也就是说「切走丢流」是前端自己的设计行为，不只是缺少订阅入口。**尚未迁移**：`useChatView.ts`(1424 行) 与 `chatStreamService.sendMessageStream`(1045 行) 仍自己建流并内联解释事件；前端无测试框架，只能靠 `npm run build` 兜类型，故未盲改。
