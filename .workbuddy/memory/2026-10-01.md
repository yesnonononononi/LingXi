## McpRegister 移除的收尾 + MCP 连接生命周期真相（同日）

## 前端：审批恢复期子会话内容逐字双写（根因 + 修复）
- 现象：批准计划/命令后恢复执行期间，子会话面板思考/正文逐字交错双写（"AllAll the the icon icon"）；根事件还会反复触发 reconcile。
- 排除用户猜想「重复点击 resume + 后端并发」：前端零调用 /resume（resume 全由 /tool-call/decide 后端内部触发）；decide 重复点击被 isSubmitting + 后端 synchronized + !isApprovalPending()→no-op emitter 挡死（用户另在 ToolCallRepository 加了 eq PENDING），空流不产生事件，不可能双写。
- 真因：双流收敛守卫提前失效。恢复期根桶两条 SSE（decide 流 + 会话级流）同播；唯一闸门 handleSessionStreamEvent 的 activeStreamCount>0 早退，但 chatApi.decideToolCall 在流建立（首事件）即 resolve，provide 的 finally 立刻把计数减到 0 → 余下恢复期会话级流不再被压制 → 同一批子会话事件被两条流各调一次 routeSessionEvent → routeToSession 对同一条 Pinia 消息 content+= 两次。普通 chat 主流不踩坑（流读完才 resolve），故只出现在审批恢复后的子代理场景。
- 修复：chat.ts decideToolCall 新增第 9 参 onSettled（流真正终局回调恰好一次，含 abort/异常；建流前 reject 不回调，三条终态路径各 notifySettled）；useChatView provide 删除 finally 回收，改为 releaseStreamCount()（幂等）挂在 onSettled，reject 路径在 catch 回收。副作用（正向）：恢复期 isSending 恒 true → 输入被禁用，与后端 beginRoot「该会话正在执行中」一致；停止/切会话的既有清零路径不受影响（幂等）。
- 卡片挂底问题用户自行在后端修（ToolCallRepository eq PENDING，只返回待审卡片），前端卡片逻辑未动。
- 验证：vue-tsc -b --force 零输出 + vite build 通过。坑：Git Bash 下 npx 被 WSL shim 劫持（sandbox 拦 wsl.exe），Windows 侧跑前端工具链要用 PowerShell + node node_modules\vue-tsc\bin\vue-tsc.js / npx.cmd。
