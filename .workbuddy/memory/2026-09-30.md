## 团队邮件「重复投递」问题（01:00-01:50）—— 结论：不是投递层缺陷

**用户报告**：session `2104978118770135040` 的双 Agent 辩论中，两名团员**独立地**报告「架构师开场立论被重复投递多次、后续针对性反驳出现丢失、多次互相指认未收到实质回复」，初判为团队邮件通路去重/投递确认缺陷。

**实测推翻了初判**（查库，不要信推测）：
- `email_message` 共 14 条，`tool_call` 表 `send_mail_to_agent` 调用**恰好 14 次**，**逐条一一对应** → 投递层没有重复写、没有串序、没有丢包。
- 唯一重复：**架构师侧同一 execution（`2104978170989219840`）发信两次**，时间 `16:54:42.103` / `16:54:44.803`（间隔 2.7 秒），内容 MD5 完全相同（`94bf8db0…`）。这是**模型的两次独立工具调用**（`call_00_uP3VB7Bb…` / `call_00_uKvJcbO7sg…`），不是投递层复制。
- 收件箱6 尾部 2 条 `PENDING` 只是辩论结束时轮次已收尾、无人消费，**不是丢包**。
- 消费侧 `consumePendingByIds` 的条件 UPDATE（`in ids` + `eq status PENDING`）+ 生效行数核对是正确的，是 e2e 正向验证，**无竞态**。

**真实根因（时序缺陷，在 `AgenticLoopInterceptor`）**：
1. 模型某轮调用 `send_mail_to_agent` → 工具完成 → **循环不挂起**（框架 `AgentLoopStepRunner` 只在 `hasNoToolCall(aiMessage)` 即该轮**零工具调用**时才挂起等待）。
2. 发信后的**下一轮**照样走 `onBeforeModelInvoke`，此时收件箱**必然为空**（对方还没回）。
3. 旧实现对「空收件箱」只做 `return`，但模型的上下文里已经累积了此前若干轮「没有新消息 / 未收到回复」的信号，**模型据此认为自己上一封没发出去** → 重发同一封开场立论。
4. 重发后才出现第一次「零工具调用」空轮 → 转入等待。**这就是这次重复的全部来源。**

**真损失（别夸大）**：多耗至少一轮模型调用；双方误判对方「重复投递」；辩论主线被元话题挤占（第 4、5 轮多封都在讨论信道问题）。**没有丢包**——「后续反驳丢失」是模型的自述，DB 里第 2/3/4/5 轮反驳全部存在且按序投递。

**⚠️ 根因校准（我先前两次写错了，以此为准）**
- **错误表述**：曾写成「拦截器主动注入了一则『没有收到回复』的催办消息，把模型推向重发」。**这是错的** —— 旧版拦截器空分支就是裸 `return`，从未注入过任何催办文案。那句「没有收到回复」是我写修复时自己新增的，我把它错记成了旧问题的诱因（回溯性归因错误）。
- **正确根因（纯时序，与拦截器注入什么无关）**：框架 `AgentLoopStepRunner` 只在**该轮零工具调用**（`hasNoToolCall`）时才挂起。模型某轮调 `send_mail_to_agent` 成功后**循环不挂起**，**立刻**进入同一执行的下一次模型调用；这一轮的上下文只有「我刚发了信 + 工具回执」，**没有任何东西告诉模型「已发出去了」**，模型遂自发再发一封。重发后才出现第一次零工具调用轮 → 转入等待。
- **时间线实证（架构师 execution `2104978170989219840`）**：`16:54:42.103` 发出#1 → `16:54:42.456` 对方发出反方开场（**353ms 就回了**）→ `16:54:44.803` 发出#2（内容 MD5 相同）。**不是「对方迟迟不回」**（对方 353ms 就回），而是**发信与等待之间缺一个「停下来」的语义**。且对方那封信即便已投递，也要等架构师**下一次** `onBeforeModelInvoke` 才被消费 —— 而那个多余的中间轮就卡在这个窗口里。
- **`LoopInterceptor` 的能力面（决定性事实）**：`LoopContext` 只给 `executionId` / `attributes`(只读) / `appendMessage(...)` 三项，七个回调**全部无返回值**。拦截器**没有「告诉循环什么」的通道，只有「往上下文塞消息」的通道**；`ExecutionControlSignal`（`requireSuspend`）**不在 `LoopContext` 里**，全仓只有 `DefaultExecutionController` 调用它。**结论：在拦截器这一层，话术是全部手段，挂起做不到。**

**修复（定案）**
- **不改拦截器**（保持裸 `return`）：用户判定这是**设计定位**问题 —— 系统本就不是让两个 Agent 聊天辩论的，mail 是**编码协作**的手递手工具，「发完即完事」，不需要等待/挂起语义。空收件箱静默 `return` 即符合该定位。
- **`ToolConfig` 的 `send_mail_to_agent` description 重写**（英文，与其余工具一致），明确四点：① 投递是**异步**的（`asynchronous`）；② 对方在其**自己的下一轮模型调用**开头才读到（`next model round`）；③ 本调用**不返回回复**（`no reply channel`）；④ 发成功后继续干自己的活或直接结束本轮，**绝不因「暂未收到回复」而重发**（`never resend`）。并点明用途是 code-collaboration hand-off、非实时往返。
- **`SendMailToAgentTool` 成功回执**与 description 同口径（英文）：`Mail delivered to agent %d. It will be read at the start of that agent's next model round. This call returns no reply, so continue your own work or end your turn; do not resend the same content.`
- `parametersJsonSchema` 的 `mailContent` 描述补充「写成自包含的完整消息，收件方无法同步追问」。

**测试**：`SendMailToAgentToolTest` 5 → **7 例**（新增：description 必须含 `asynchronous`/`next model round`/`no reply channel`/`never resend`；回执含 `delivered`/`next model round`/`do not resend`）。7/7 绿。

**排查方法论（值得复用）**：报告「投递缺陷」先对齐 **`tool_call` 次数 vs `email_message` 行数**，再看**是否同一 execution 发了两次**。`tool_call.raw_input` 是模型真实意图的权威记录 —— 次数相等则投递层无辜，问题在「模型为何决定再发一次」。另外：**模型自述的「我没收到 X」是自述，不是事实**，必须回 DB 核对。

## Token 用量确实没被保存（17:04 诊断，未实施）

**结论：对，没保存。三层证据**
1. **框架有统计**：`DefaultConversationManager:80` 每轮 `execution.getTokenUsage().add(...)`；`LocalExecutionRepository.save` 序列化进 `execution.snapshot`。实测快照里有真值（字段名 `totalTokens/inputTokens/outputTokens`，最近一次完成的执行 totalTokens=2,800,334）。
2. **LingXi 侧落库链路是死的**：`SessionPO.total_tokens/input_tokens/output_tokens` 三列在、`Session.addTokenUsage`（`Session.java:98`）在、repository 双向映射在（`SessionRepositoryImpl:92/98/108`）、`SessionVO` 下发在、创建时初始化 `TokenUsage.empty()`（`SessionServiceImpl:76`）—— 但 **`addTokenUsage` 在 src/main/java 零调用**。
3. **前端只吃瞬时事件**：`ExecutionCompleteEvent.TokenInfo(inputTokenCount/outputTokenCount/totalTokenCount)`（注意与 `TokenUsageEntity` 字段名不同）只在 `EXECUTION_COMPLETED` 出现一次；`ChatMessageItem.vue` 的 `displayTokens` 先读气泡 `tokens/tokenInfo`、再回落 `sessionTokenInfo`（会话级，全 0）→ 刷新后 token 展示消失。

**两个坑（修的时候必须处理）**
- **重复累加**：resume 之后再完成会**再发一次** `EXECUTION_COMPLETED`（带该执行的最终累计值）。按「增量累加」会把同一执行算两遍 → 需要按 execution 幂等（台账表 `execution_token_usage(execution_id PK, session_id, ...)` + `ON DUPLICATE KEY UPDATE` 覆盖为最终值；会话聚合=SUM 台账，天然幂等且天然覆盖子会话）。仅给 `session` 三列做 `+=` 是错的。
- **口径**：`totalTokens` 是「该执行所有轮次的计费累加」（每轮 input 都重算整段上下文，所以一次 run 2.8M 很正常），**不是「上下文大小」**。若 UI 想表达上下文规模应取末轮 input；想表达计费就累加。需用户定口径。
- 若实现：挂 `RuntimeListener.onExecutionCompleted`（与 `ExecutionErrorTranscriptListener` 同型同层，经 `executionIdentity.sessionId` 定位会话，覆盖根与子代理），不要挂 `ChatServiceImpl.executePrepared`（decide 恢复与子代理完成都不走它）。
