## 核查：tool_call 表是否保存失败/取消的调用历史（结论：保存了，但不在 status 上）

写入路径（行号级证据）：
- 落行：`ToolCallExecutionListener.onToolCall` → `registrar.markExecuteStarted`（框架 `invokeTool` **之前**回调，幂等 UPSERT，EXECUTE 行为 `in_progress`；PROMISE 行为 `pending`）
- 收尾：`onToolCallOutput` → `ToolCallOutcome.fromFrameworkStatus(框架 resultStatus)`（**null 也判 FAILED**）→ `registrar.completeExecute` 写 `raw_output.outcome`；`ToolCall.complete()` 把状态推到 `completed`，且**终态幂等**（已 completed 不覆盖结论）
- 审批类：`CommandApprovalExecutor:135-146`（CANCELLED / REJECTED / APPROVED）、`ToolCallServiceImpl.decide` → `decisionOutcome`（APPROVED/REJECTED/ANSWERED）
- 执行终结：`ExecutionLifecycleAdapter.onExecutionFinished`（完成/失败/取消三条都触发）→ `ToolCallService.cancelPendingToolCalls` → 该执行下 **pending** 行 `complete(converter.cancelled("执行已取消"))`
- outcome 枚举 7 个：APPROVED / REJECTED / ANSWERED / CANCELLED / SUCCEEDED / FAILED / TIMED_OUT
- 前端确按 outcome 判：`utils/session.ts:377-383`（SUCCEEDED→success；FAILED/REJECTED/TIMED_OUT/CANCELLED→failed；其余 unknown）

两个限制：
1. `status` 只有三态，失败/取消**无法在 status 列上筛**，必须解析 LONGTEXT `raw_output.outcome`
2. **`in_progress` 缺口**：`cancelPendingToolCalls` 只遍历 `listPendingByExecutionId`（仅 pending）→ 工具已开始但 END 事件未到就中断的行永久停在 `in_progress` 且 `raw_output` 为 null；`ExecutionStartupReaper` 不碰 tool_call；前端按 unknown 降级（`utils/session.ts:497-515`）

对上一轮「移除 AI 行 toolCalls」的影响：失败/取消的调用**在 tool_call 里是有行的**，所以 AI 行 toolCalls 的独有价值进一步收窄到「模型请求了、但一条结果行都没产生」的那一类 —— 失败/取消不属于这一类。已把上述事实补进项目 MEMORY.md §二。

## 核查：LoopInterceptor 能否拿到工具执行结果（结论：能，但不该用它写库）

- **能拿到**：`LoopInterceptor.onAfterToolCall(LoopContext, List<ToolExecuteResult>)` = 本批全部结果，每个请求的调用一条，含失败。`DefaultToolExecutionManager:128-167` 把一切都转成 result 而非抛异常：`Tool not found`→REJECTED、不在白名单→REJECTED、策略拦截→REJECTED、超时→`err("tool execution timeout after Ns")`+TIMED_OUT、被中断→`err("tool execution interrupted")`+CANCELLED、执行抛错→catch Throwable→`err("Tool execution error...")`+FAILED。每条经 `identified(...)`(`:320-327`) 盖章 `id=request.id()`（模型下发的 call id）与 `toolSpecification`；结论读 `code`(1/0)、`toolResultType`(NORMAL|PROMISE)、`isSuccess()`/`isPromise()`
- **不建议用它替换写库路径**（三条）：① 契约 "Pre/processing callback failures fail the run"，`onAfterToolCall` 三处调用点（`AgentLoopStepRunner:103/115/132`）**无 try/catch** → 里面写库会把 DB 抖动变成整轮 FAILED（只有 `onLoopEnd`/`onRunEnd` 是 catch+log）；② 粒度每**批**一次，而 `RuntimeListener.onToolCallOutput` 每**个工具**一次且与开始事件成对；③ 顺序更晚（manager `publishEndEvent` → `appendMessage` → `onAfterToolCall`）
- **唯一会丢结果的路径**：`DefaultToolExecutionManager.executeTool` 的 `ExecutionException` 分支 `throw cause`(`:281`) → 整批失败，无 `onAfterToolCall`
- **它能补的是「批次异常终止」的兜底**：`onRunEnd(Execution)` 仅 COMPLETED/CANCELLED/FAILED 触发（SUSPENDED 不触发），在 `clear()` 的 finally 里调（loop 抛异常也会到）、异常只 log，且带完整 `Execution`（含 messages）→ 适合按 call id 对账 tool_call。**进程被杀**时任何进程内回调都无效 → 只能靠启动收尸，而 `ExecutionStartupReaper` 目前只收 execution 行、不碰 tool_call（这是唯一要新增的地方）
- **落地约束**：框架只注入一个 `LoopInterceptor` bean（`ExecutionRuntimeConfig:39`），LingXi 现有实现 `AgenticLoopInterceptor`；新增钩子必须加在该类内，另起 `@Component` 会让启动期注入歧义

## 桌面端：exe 启动时静默拉起后端 + 内置 JRE

**目标**：双击 Electron 打包出的 exe，后端随之启动、全程无黑窗口、且不依赖用户机器上的 Java。

**新增/改动**
- 新增 `frontend/electron/backend.cjs`：后端生命周期（定位产物 → 复用探测 → spawn → 就绪等待 → 收尾杀进程）
- 新增 `frontend/scripts/build-backend-runtime.mjs`：`mvnw package` + `jlink` + 自检，产物落 `frontend/build/backend/{app.jar,runtime/}`
- `frontend/electron/main.cjs`：加单实例锁、启动遮罩窗口、`await backend.start()` 后再建窗口、`will-quit` 异步收尾
- `frontend/package.json`：`extraResources: [{from:"build/backend", to:"backend"}]` + `backend:runtime` / `backend:runtime:quick` 脚本，`app:build*` 前置该脚本
- `frontend/.gitignore`：忽略 `/build/`

**关键技术点（都是真会踩的）**
1. **无黑窗口**：必须用 `javaw.exe`（GUI 子系统，不挂控制台），`windowsHide: true` 只是兜底；一旦 stdio 改成 `inherit`，用 `java.exe` 黑窗口立刻回来。
2. **就绪判据**：`进程活着 ≠ 服务可用`，必须 TCP 探测 8088，不能 sleep。进程提前退出要 `break` 而不是等满 90s。
3. **退出收尾**：Windows 父进程退出**不会**带走子进程，必须 `taskkill /pid <pid> /T /F`（`/T` 连子进程树）。`will-quit` 里异步收尾要 `preventDefault()` 后收完再 `quit()` 一次。
4. **端口复用**：8088 已被占（IDE 里跑着后端 / 上次崩溃的孤儿 JVM）时直接复用、不杀，避免「端口占用」启动失败。
5. **单实例锁**：端口固定 → 必须 `app.requestSingleInstanceLock()`，否则多开必撞端口。前端 `apiConfig.ts` 桌面端默认地址写死 8088，所以端口不能随便改。
6. **cwd 选 userData**：`application.yaml` 的 `optional:file:.env` 按 cwd 解析，装到 Program Files 后 jar 旁边不可写。用户把 `.env` 丢进 userData 即可。
7. **jlink 模块清单**（18 个）里 `java.desktop`（Spring BeanWrapper 用 `java.beans.Introspector`）、`jdk.unsupported`（sun.misc.Unsafe）、`jdk.crypto.ec`（调 LLM 的 HTTPS）、`jdk.charsets`、`jdk.localedata` 一个都不能少；真缺的症状是运行期 `NoClassDefFoundError`，兜底 `--all-modules`。

**验证（实测）**
- `jlink` 精简 JRE **59.6MB**、fat jar **47.9MB**；用精简 JRE 实测启动后端：`Started LingXiApplication in 11.248 seconds`、Tomcat 正常监听、**零 `NoClassDefFoundError`/`ClassNotFoundException`**。
- `electron-builder --dir` 打包后布局核对通过：`resources/backend/app.jar` + `resources/backend/runtime/bin/{java,javaw}.exe` 均在位（与 `resolveLayout` 预期一致）。

**本机 maven 变通（写进脚本了）**：`./mvnw` 坏的（`.mvn/wrapper` 缺 jar）；`mvn` 经 Git Bash 会把 POSIX 路径喂给 Windows java，报 `ClassNotFoundException: classworlds.launcher.Launcher`。脚本 `resolveMaven()` 检测到 wrapper jar 缺失时，自动改用 `java -classpath <boot>/plexus-classworlds-*.jar -Dclassworlds.conf=... -Dmaven.home=... org.codehaus.plexus.classworlds.launcher.Launcher`，绕开 shell 路径转换。

## 数据库选型调研：换掉 MySQL 的迁移成本

用户问「不用 MySQL 还有什么推荐」。**结论：H2 文件模式最合适**。

决定成本的关键事实（全部 grep 实测）：
- **零 XML mapper**：`src/main` 下没有任何 `.xml`，全走 MyBatis-Plus `BaseMapper` + LambdaQueryWrapper → SQL 基本方言无关。
- **方言只有一个硬编码点**：`MybatisPlusConfig.java:20` `new PaginationInnerInterceptor(DbType.MYSQL)` → 换 `DbType.H2` 一行。
- **零 MySQL 专有函数**（无 `ON DUPLICATE KEY`/`IFNULL`/`GROUP_CONCAT`/`DATE_FORMAT`/`INSERT IGNORE`）。MySQL 味道全在 `init.sql` 的 DDL：15 张表，`BIGINT AUTO_INCREMENT`/`DATETIME(3)`/`JSON`/`ENGINE=InnoDB CHARSET=utf8mb4`/`COMMENT`/14 处 `ON UPDATE CURRENT_TIMESTAMP`。
- **JSON 列不依赖 DB 类型**：`McpRepositoryImpl` 把 `headers`/`env` 当 JSON 字符串存取 → `TEXT/CLOB` 即可。
- **`FOR UPDATE`**：`EmailRepositoryImpl:82` `.last("FOR UPDATE")` → H2/PostgreSQL 支持，**SQLite 不支持**（无行锁，语法错误）。
- **`DuplicateKeyException`**：仅 `EmailServiceImpl#obtainMailbox:188` 一处，其 javadoc 自己写明「MySQL 唯一键冲突不中止事务，不像 PostgreSQL 会把事务置为 aborted」→ **PostgreSQL 与该模式天然冲突**（要改 `ON CONFLICT` 或加 savepoint）。
- **`LIMIT`** 出现在 4 处 `.last("LIMIT n")`（ExecutionIdentity:72、ExecutionRepositoryImpl:52、McpRepositoryImpl:63、SessionMessageRepositoryImpl:48）→ 三家都支持。
- **主键**：`IdType.AUTO`（DB 自增）7 个 PO；`IdType.INPUT`（雪花）3 个 PO（session_message/session_context/email）。
- **`update_time` 双写**：DDL 有 `ON UPDATE CURRENT_TIMESTAMP`，代码也有 8 处显式 `.updateTime(...)`；但 **H2/SQLite/PG 都不支持 `ON UPDATE`** → 建议补 `MetaObjectHandler`（项目当前没有）。
- **H2 已有先例**：`src/test/resources/*-schema.sql`（4 张表）是手改的 H2 镜像，`email-schema.sql:16` 已建 `uk_email_workflow_recipient`，邮件链路测试在 H2 跑通。

**顺带发现**：`docker-compose.yml` 的 `redis:8` 是死配置 —— `pom.xml` 无任何 redis 依赖，`src/main` 里 `redis` 只出现在 javadoc 比喻中。

## 修复：已决断卡片以未决断样子常驻页底

**症状**：用户答过的 Clarify 卡片仍渲染成完整作答表单（选项 + 禁用态「提交」），一直占在会话列表底部；同一张卡片在消息流里另有一份正确的折叠行 —— 即**同一轮次出现两条气泡**。

**取证（结论：纯前端问题，服务端全对）**
- `GET /session/{id}/messages` 与 `GET /tool-call/{id}` 两个接口对该卡片都返回 `type=PROMISE status=completed pending=false rawOutput.outcome=ANSWERED`。
- DB `tool_call` 行 `completed/ANSWERED`；`session_message` 里只有**一条** TOOL 行引用它。
- 探针（`aggregateSessionMessages` + 真实接口 JSON）：8 条消息，最后一条 assistant 带 2 张卡片，**都 `pending=false`** → 历史聚合正确。

**根因（三个缺陷叠加）**
1. `messageRouter#initTurn`（`chatSessionStore`）在审批恢复时**复用该轮既有 assistant 气泡**，并把 `existingAi.isComplete = false`、`isThinking = true`。
2. `services/chat.ts#decideToolCall` 给恢复流的气泡钉了一个**全新本地 id**（`createLocalId('msg-bot-resume')` + `Object.assign(botMessage, updatedMsg, { id: botMsgId })`），而 `useChatView#applyStreamMessage` 是**按 id 合并**的 → 找不到就 `push` → **多出第二条气泡**。这条副本手里的卡片还是 `CARD_PENDING` 那一刻建的（`pending=true`），结论落库后它不会自己刷新。
3. `useChatHistory#mergeAuthoritativeMessages` **无条件保留** `role==='assistant' && isComplete === false` 的气泡 → 重复气泡每次对账都被保留，永远清不掉（对应「一直占位」）。

探针复现：`mergeAuthoritativeMessages([...serverMsgs, staleLocal], serverMsgs, now)` → 该轮次 **2 条 assistant 气泡**，其中一条 `CHOICE(pending=true)`。

**修复（2 处）**
- `views/chat/useChatView.ts#applyStreamMessage`：按 id 找不到时，再按 **turnId** 归并到该轮既有 assistant 气泡（同一轮次只应有一个气泡，与历史聚合同口径）。
- `views/chat/useChatHistory.ts#mergeAuthoritativeMessages`：对账后**保留下来的本地气泡**若与服务端同轮次，`promptCards`/`promptCard` 一律换成服务端权威值（仅当服务端该轮确有卡片时）。

**验证**：探针修复后同一场景卡片 `pending=false`；`vue-tsc -b --force` EXIT=0 零输出；`npm run build` ✓ 19.06s；`tests/crossPageTurn.test.ts` **7/8**（唯一红的用例 2 是同日 `utils/session.ts`「终结轮次」改动造成的既有失败，与本次无关；用例 7「相同轮次恢复复用原有回答气泡组」通过）。

**附带更正**：`decideToolCall` 里那句注释「router 在 EXECUTION_STARTED 时会 `initExecution` 造出新 id 的 store 消息」**前提是错的** —— `chatSessionStore` 里**没有** `initExecution`，只有 `initTurn`，而 `initTurn` 是**复用**既有气泡。钉新 id 正是重复气泡的来源。

**H2 落地要点**：pom 去掉 `<scope>test</scope>`；`DbType.H2`；新增一份 H2 版 DDL（纳入「三处同步」规则）；补 `MetaObjectHandler`；URL 用 `jdbc:h2:file:<userData>/data/lingxi;MODE=MySQL;DATABASE_TO_LOWER=TRUE`。注意 H2 2.x 保留字（`VALUE`/`KEY`/`USER`/`YEAR`…）可能需 `NON_KEYWORDS`，`session` 表名待实测。

**概念澄清 + 实测（用户追问「文件模式怎么阐述行/表/索引，MP 能读吗」）**
- 用本地 h2-2.3.232 真跑了一个文件模式库：建 `tool_call` 表 + 1 个二级索引 + 3 行 → **磁盘上只有 1 个 20KB 的 `lingxi.mv.db`**。`INFORMATION_SCHEMA` 实测：catalog=`LINGXI`、schema=`PUBLIC`、table=`TOOL_CALL`(BASE TABLE)、索引 `PRIMARY_KEY_8`(PRIMARY KEY,唯一,ID) + `IDX_TOOL_CALL_CONV`(INDEX,非唯一,CONVERSATION_ID+ID)。
- 关键认知：**表/索引各是一棵 B-tree，不是「文件里的区域」**；写入是 append-only（UPDATE = 追加新版本 + 改 root 指针），删数据不会自动缩文件，要 `SHUTDOWN COMPACT`；一个文件 = 一个**数据库**（不是一张表），15 张表也只是一个文件。
- **MP 能读，且项目已证明**：`ToolCallPersistenceTest:41-45` 用 `EmbeddedDatabaseBuilder().setType(H2)` + `MybatisSqlSessionFactoryBean` + `ToolCallMapper` 真实跑通 —— MP 的抽象层是 JDBC，换文件模式只差一个 URL。**零 XML mapper → 一条 SQL 都不用改**；`BaseMapper`/`LambdaQueryWrapper`/PO 注解/`@Transactional` 全部原样可用。要改的只有 4 处（见上）。
