## git 对象库损坏修复 + root-commit 重建（17:57-18:10）

**现象**：`git commit` 报 `error: invalid object 5120a629... for '.workbuddy-ai/memory/2026-09-27.md'` + `Error building trees`。

**根因**：rebase 事故已摧毁对象库——436 个暂存条目中 **309 个 blob 在对象库彻底消失**（全库枚举 562 对象 = 113 松散 + 449 pack；pack `pack-8291351f` 本身完好但不含丢失对象）。分支 unborn（`feature/agent` 无任何提交）、无其他分支/reflog 对象可找回，唯一恢复源=工作区磁盘文件。

**关键坑（可复用教训）**：直接 `git add` 这些文件**静默无效**——索引 stat 缓存命中（磁盘内容哈希=索引旧哈希）→ git 认为"内容没变"→ 沿用指向死对象的 oid，**不重写对象**。必须 `git rm --cached` 抹掉索引条目（清 stat 缓存）再 `git add`，才会真正重算哈希写对象。单文件验证后批量套用。

**修复流程**：
1. `git ls-files -s | awk '{print $2}' | git cat-file --batch-check` 过滤 `missing` 得缺失清单（309 个）
2. 逐路径 `git rm --cached` + `git add` → 索引缺失归零、条目数 436 不变
3. `git commit` → **root-commit `dae2329`**（436 files, 48877 insertions），工作区干净

**遗留状态**：
- HEAD reflog 全是死指针（fsck 报 `invalid reflog entry`，无害，未清理）
- 远端 `origin = https://github.com/yesnonononononi/LingXi`（fetch/push 可用，未推送本次提交）

## 排查「DB 配 stdio，框架却走 streamableHttp」+ 404（23:00-23:15，**结论已被下节推翻，仅存取证过程**）

> ⚠️ 本节结论错误。真实原因是 Windows 上裸 `npx` 无法执行，且 404 来自 github server、与 playwright 无关。见下一节「【推翻上节结论】」。保留本节以记录静态取证方法（对排查仍有价值：证明了 DB/parse/switch/多态 JSON 全链路无缺陷）。

**现象**（用户提供栈）：`RuntimeException: Unexpected status code: 404` at `StreamableHttpMcpTransport.lambda$execute$0:301` + `MCP server playwright connection failed (RuntimeException); continuing without its tools`。

**逐层取证（全部实测，非推断）**
1. DB 值干净：`docker exec LingXi-mysql mysql -uroot -proot LingXi -e "SELECT transport,LENGTH(transport),HEX(transport) ..."` → playwright `stdio` / len 5 / hex `737464696F`，**无空格无大小写问题**；三条均为 `github`+`context7`=streamable-http、`playwright`=stdio、status 全 1

## 【推翻上节结论】实跑定位真因：传输选对了，是 Windows 上裸 `npx` 起不来（23:15-23:25）

**上一节的"旧产物"推断是错的**。真跑一遍就推翻：传输选择完全正确，404 是**另一件事**。

**实跑取证（8094 端口起 jar，`-Dlogging.level.dev.langchain4j=DEBUG`）** —— DEBUG 日志里出现决定性两行：
```
DEBUG d.l.m.c.t.stdio.StdioMcpTransport : Starting process: [npx, @playwright/mcp@latest]
WARN  c.s.h.s.config.mcp.AgentMcpProvider : MCP server playwright connection failed (RuntimeException)
```
**框架走的是 `StdioMcpTransport`，不是 `StreamableHttpMcpTransport`** —— 之前的怀疑方向彻底错了。

**两个问题被混为一谈，实际是独立的两件事**
1. **那条 404 与 playwright 无关**：`List-change subscription failed` 来自 **github** server（紧接其后的 DEBUG 是 `MCP server discover result: github-mcp-server`），线程 `ient-4-Worker-*`；而 playwright 失败在 `onPool-worker-1`，时间差 2 秒。github 的 `resources.listChanged` 订阅返回 404 是**无害噪音**，不影响工具加载
2. **playwright 真因：Windows 上 `npx` 裸命令无法执行**。`StdioMcpTransport.start` 用 `new ProcessBuilder(command).start()`；Windows 的 `npx` 是**无扩展名的 sh 脚本**（同目录只有 `npx.cmd` 可执行）→ `start()` 抛 IOException → `AgentMcpProvider` catch 后 warn 并降级

**修复与验证（已实测通过）**
- 库中 command 改为 `["npx.cmd","--yes","@playwright/mcp@latest"]`：`docker exec LingXi-mysql mysql ... -e "UPDATE mcp SET command='[\"npx.cmd\",\"--yes\",\"@playwright/mcp@latest\"]' WHERE name='playwright'"`
- 重启后日志：`Starting process: [npx.cmd, --yes, @playwright/mcp@latest]` → **`Opened 72 MCP tool(s)`**（原 47，+25 即 playwright），**无 connection failed**
- 问 agent：确认有 30 个 `mcp_playwright` 工具，前缀为 `mcp_context7` / `mcp_github` / `mcp_playwright`
- 端到端实调：`用 playwright 打开 https://example.com 并告诉我页面标题` → 返回 **`Example Domain`** ✅

**关键教训**
- **不要用静态读码替代实跑**。上节读完所有源码后得出"代码没问题、疑似旧产物"，实跑一遍 5 分钟就推翻 —— 真因是环境（Windows 裸命令），静态分析永远看不到
- **同一时间窗内的多条报错未必同源**。404 与 playwright 失败时间相近但来源/线程都不同，先入为主把它们当成因果，导致方向跑偏
- **框架 `AgentMcpProvider` 日志是排查盲区**：只打 `server.name() + failure.getClass().getSimpleName()`，既不打 transport、不打 URL、不打原始异常 message。本例中 `StdioMcpTransport` 已经把 `Starting process: [...]` 打到 DEBUG，但默认级别看不到。**排查 MCP 必开 `logging.level.dev.langchain4j=DEBUG`**
- 无效探测动作复盘：`npx --version` 报乱码 + 沙箱提示 wsl.exe 被拦，是 Git Bash 下裸 `npx` 不可用的**同一现象**，当时未识破；`cmd //c` 被安全策略拒绝（"Invoking cmd.exe from Bash bypasses all command validation"）也不影响结论——应用进程根本不经过 bash
