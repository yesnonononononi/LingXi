## 修复：v3 思考过程（thinking）提交后丢失 + 「正在探索中」动画不出现

用户报：「思考过程信息都没有被展示出来，而且发出消息的一瞬间到加载的过程，loading 动画也没有出来（正在探索中）」。

### 证据先行（这次没靠读代码推演，两次教训换来的）

- **后端全给了**：真实抓帧统计 = `THINKING_DELTA 50~86 帧`、`RESPONSE_FINALIZED.data.thinking` 有完整文本、
  bootstrap `history.records[AI].thinking` 有值。**`MESSAGE_COMMITTED` 载荷只有 `text`，不含 `thinking`**。
- 用**真实 store + 逐字重放真实帧**跑复现（`tsx` 直连 `streamV3Store` + `projectSessionMessages`），
  确认思维链在 `MESSAGE_COMMITTED` 那一刻从 `thoughtSteps` 归零。

### 根因 A：thinking 在提交环节断链（前端）

`streamV3Store.applyMessageCommitted` 的 AI 分支把活响应绑定 `messageId` 后，
`projectSessionMessages` 的 `live` 过滤条件 `slot.messageId == null` 立即把它排除；
改由**历史行**承载 —— 而 `appendCommittedRow` 写入的 history 行**只有 `text`，没有 `thinking`**。

于是：流式那几秒思考在活响应槽里能显示，**一旦提交（`MESSAGE_COMMITTED` 到达）就整段消失**。

**修**（`streamV3Store.ts`）：AI 提交时从活响应槽取 `current.thinking`，一并写进 history 行：

```ts
let thinking: string | undefined;
if (streamKey) {
  const current = ensureResponse(streamKey, event);
  ...
  thinking = current.thinking || undefined;
  ...
}
appendCommittedRow(sessionId, { id, turnId, type, text, thinking, streamKey });
```

只有"实时提交"这一条断），改协议属多余且要前后端同步升级。

### 根因 B：派生回答气泡从不设 `isExploring`（前端）

- `isExploring` 全仓只有 **2 处赋值**：`useChatView.ts:383` 与 `sessionRunState.ts:21`（都是补骨架），
  **`messageProjection` 从不设它** → 派生气泡（`msg-live-*`）永远 `isExploring=undefined`

## 第二轮 QA 返工：F1 暂存溢出恢复 + 终态对账三条边界（10-05 下午）

### F1 —— 暂存溢出必须主动恢复（不只是拒绝旧快照）

**根因**：溢出发生在帧 ingest 路径（store 内部 `stage()`），它只 `abortSync`（作废 token + 打回 idle）
就返回，**不会**抛到协调器 `runBootstrap` 的 await 链上。协调器只处理自己那次请求的失败
（`!isOk` / `catch`），于是这个出口没人接 → 界面停在 idle，SSE 连接虽在但服务端不再发 READY
→ 本次缺失的历史与卡片**永久**补不回来。

**修**（三处联动，缺一不可）：

1. `streamV3Store`：`applyBootstrap` 签名 `void → boolean`，只有走到末尾（`setPhase(live)` 之后）
   才 `return true`；代次 guard 拒绝的 `return false`。**末行 `return true` 极易漏** —— 漏了则
   所有快照都被判为「未接纳」，正常路径也被当失败。
2. `streamV3Store`：新增 `syncFailureSeq = ref<Record<string, number>>({})`，**每个失败出口**递增
   （当前唯一出口 `abortSync`），并加入 `return {}` 导出。它与 `syncPhase` 的区别：phase 语义是
   「现在在哪一步」，观察 idle **分不清**「刚失败」还是「本来就在 idle」。
3. `streamV3Sync`：新增 `watch(() => store.syncFailureSeq[key], ...)`（`flush: 'sync'`），
   非 live 即 `scheduleRecovery()`；`detach` 里 `stopFailureWatch()`。
   同时 `runBootstrap` 改为按 `applyBootstrap` 返回值记账：**未接纳不得清零 retryAttempt**。

**验证日志（证明真走了溢出路径，非空断言）**：
```
[streamV3] 暂存缓冲溢出，放弃本次同步: 100
[streamV3Sync] 同步失败，登记退避恢复: 100 第 1 次，延迟 1000ms
[streamV3Sync] bootstrap 快照未被当前代次接纳，保留恢复机会: 100
```

## 第三轮 QA：撤销上轮的 SUSPENDED 语义误改 + 根代际守卫收窄（10-05 晚）

**上轮结论被推翻，本次是纠错，不是新增。**

### ① 上轮把 SUSPENDED 从终态谓词里删掉是错的（我改了设计契约去迎合自己的判断）

`docs/stream-protocol-v3-design.md` §8.1 逐字规定：**execution 的终态或 SUSPENDED，无论来自实时事件
还是 bootstrap，都通过同一状态转换结束相关响应的进行态**（路径 2），路径 4 要求定格后的迟到
STARTED/DELTA 不得复活响应。我上轮看到后端 `TERMINAL_THRESHOLD = COMPLETED` 就断言「SUSPENDED 不是终态」，
并把它从 `EXECUTION_TERMINAL_STATES` 删掉，还**反过来改旧测试**去迎合 —— 双重错误。

**真正的错**：一个谓词名 `resolveExecutionTerminal` 承担了两个语义。执行生命周期 ≠ 单个 streamKey 的响应生命周期。

正确修法是**拆谓词**（`src/utils/streamV3.ts`）：
- `resolveExecutionTerminal` = COMPLETED/FAILED/CANCELLED —— 只用于「本轮收尾了、要不要对账」
- `resolveResponseClosed` = 三终态 + SUSPENDED —— 用于「这段还能不能收增量」（`finalizeByExecution`）

三个调用点的归属：
| 调用点 | 用哪个 | 理由 |
|---|---|---|
| store bootstrap `executions[].status` → finalize | `resolveResponseClosed` | §8.1 路径 2 |
| store 实时 `EXECUTION_UPDATED` → finalize | `resolveResponseClosed` | 同上，两条路径必须等价 |
| `useChatView` D6 终态对账 watch | `resolveExecutionTerminal` | 挂起还会恢复，对账是白花查询 |

**教训**：谓词名出现「Terminal / Closed / Finished」混用时，先问「它答的是哪个问题」，再决定集合内容；
发现测试与新判断冲突时，**先查设计文档谁是权威**，不要先改测试。

### ② 全事件根代际守卫与 SESSION_UPDATED 生产口径冲突（真 bug，上轮引入）

`isStaleFrame` 拿每一帧的 `historyRevision` 比根代际。但
`CommittedStateV3Observer.publishSessionUpdated:158` 填的是 **`session.getHistoryRevision()`（实体自身）**；
而 `Session.historyRevision` 默认 `1L`，`SubSessionResolver.createSubSession` **不继承**根代际。

→ 根重发后 revision=2，新建子会话 revision=1，其合法 SESSION_UPDATED 被判「旧代际」丢弃
→ 子会话不进 `sessions` 槽 → 子面板、卡片冒泡、根子范围判定全失灵。日志形态：
`[streamV3] 旧代际帧，已拒绝: SESSION_UPDATED 1 < 2`

**修**：代际判据只对**信封 revision 真表示根代际**的帧生效；实体类帧（`SESSION_UPDATED`/`TURN_UPDATED`）
跳过代际判据，交给各自的 `version` 比较（`shouldApply`）—— 实体只有新旧，没有「属于哪一代历史」。
身份判据（turnId/executionId 作废登记）对**所有帧**保留，所以 F2 的复活反例仍挡得住（探针实测：
`TEXT_DELTA` 旧代际+已作废身份仍被拒，`SESSION_UPDATED` 子实体 revision=1 放行）。

后端补契约测试 `CommittedStateV3DeliveryTest#subSessionUpdatedCarriesItsOwnRevisionButRoutesToRoot`：
走真实仓储 → 断言信封 revision=1（实体自身）+ 阴性对照根 revision=2 + 仍路由到根连接。
