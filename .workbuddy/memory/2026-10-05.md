## 第三轮：接「停止生成」断点（前端，已绿，未 commit）

用户只写流式渲染逻辑，故本轮的「停止生成」只接**断点**（中断在途请求），不做渲染。

### 病灶

`handleSendMessage` 从未给 `currentAbortController.value` 赋值 → `handleStopGeneration`
的 `abort()` 一直打在 `null` 上；`chatStream`/`resendStream` 虽已接受 `signal?: AbortSignal`
但无人传。另发现两个连带断点：

1. `isSending` 依赖 `runStatus === 'RUNNING'`，而 `runStatus` **只在
   `reconcileSessionAfterStream` 里刷新** → 停止后不刷新则 `isSending` 永久卡 true，
   用户点完停止反而发不出下一条。
2. `handleStopGeneration` / `handleSelectSession` 里 `activeStreamCount.value = 0` 硬清零
   与 `finally` 的递减重复，且会抹掉其它会话的在途状态。

### 改动（4 处，均在 frontend）

- `services/agent.ts`：补 `export const isAbortError`（随 `sseRouter` 被删的判定工具，
  最小实现：`error instanceof DOMException && name === 'AbortError'`）
- `views/chat/useChatView.ts`：
  - `handleSendMessage` 创建 `AbortController` → 赋 `currentAbortController.value` →
    两个流式调用末尾传 `controller.signal`；`catch` 里 `isAbortError` 静默（不弹失败提示、
    不写 `sendFailureNotice`、跳过历史对账）；`finally` 只在 `currentAbortController.value === controller`
    时置空，且 abort 时跳过计数递减
  - `handleStopGeneration`：`/stop` 成功后补 `reconcileSessionAfterStream` 刷新 `runStatus`；
    去掉 `activeStreamCount.value = 0`
  - `handleSelectSession`：去掉 `activeStreamCount.value = 0`

### 实测（探针，非读代码推演）

`abort` 打在两个阶段的行为不同，已用 node 探针实测：

| 阶段 | `await fetch` 表现 | `isAbortError` 能否兜住 |
|---|---|---|
| 等服务端响应头 | reject `DOMException/AbortError` | ✅ |
| 已拿到头、读 body 时 | `await fetch` **已 resolve**，abort 只中断 body 读取 | ✅（但当前代码不读 body） |

第三条实测：前端 `abort()` 后服务端 `req.on('close')` 触发 → **能切断连接**。
⚠️ **连接断开 ≠ 停止后端执行**，执行终止仍靠 `POST /stop`，两者缺一不可。

### 遗留（交给用户的渲染环节）

- `await chatStream(...)` 拿到 `Response` 却没读 body，故 `reconcileSessionAfterStream`
  在服务端尚未生成时就拉了历史 → 停止后看到的仍是中间态。**这是改造前既有行为，非本轮引入**，
  等用户写流式渲染时一并解决
- `activeStreamCount` 语义已退化为「请求在途计数」，不再是「生成中」

## 第二轮 QA 返工：F1 暂存溢出恢复 + 终态对账三条边界（10-05 下午）

### F1 —— 暂存溢出必须主动恢复（不只是拒绝旧快照）

**根因**：溢出发生在帧 ingest 路径（store 内部 `stage()`），它只 `abortSync`（作废 token + 打回 idle）
就返回，**不会**抛到协调器 `runBootstrap` 的 await 链上。协调器只处理自己那次请求的失败
（`!isOk` / `catch`），于是这个出口没人接 → 界面停在 idle，SSE 连接虽在但服务端不再发 READY
→ 本次缺失的历史与卡片**永久**补不回来。

**修**（三处联动，缺一不可）：

1. `streamV3Store`：`applyBootstrap` 签名 `void → boolean`，只有走到末尾（`setPhase(live)` 之后）
   才 `return true`；代次 guard 拒绝的 `return false`。**末行 `return true` 极易漏** —— 漏了则
   所有快照都被判为「未接纳」，正常路径也被当失败。
2. `streamV3Store`：新增 `syncFailureSeq = ref<Record<string, number>>({})`，**每个失败出口**递增
   （当前唯一出口 `abortSync`），并加入 `return {}` 导出。它与 `syncPhase` 的区别：phase 语义是
   「现在在哪一步」，观察 idle **分不清**「刚失败」还是「本来就在 idle」。
3. `streamV3Sync`：新增 `watch(() => store.syncFailureSeq[key], ...)`（`flush: 'sync'`），
   非 live 即 `scheduleRecovery()`；`detach` 里 `stopFailureWatch()`。
   同时 `runBootstrap` 改为按 `applyBootstrap` 返回值记账：**未接纳不得清零 retryAttempt**。

**验证日志（证明真走了溢出路径，非空断言）**：

### ★ 顺带挖出的真 bug：`SUSPENDED` 被前端当终态（后端不是）

`EXECUTION_TERMINAL_STATES` 含 `SUSPENDED`，但后端权威是
`ExecutionStatusCodes.TERMINAL_THRESHOLD = COMPLETED(3)`，`isTerminal` 判 `>= COMPLETED`
→ **SUSPENDED(2) 不是终态**（`StreamRoundRegistry` 亦以 `EXECUTION_SUSPENDED` 作「非终态中断」分支，
只定格**未被返回**的轮次）。把挂起当终态有三处错：对账提前触发、思考指示器提前收起、
活响应被误判「未接收完整」。

修：`resolveExecutionTerminal` 只保留 `COMPLETED / FAILED / CANCELLED`。
连带改三条旧断言（它们把错语义写成了契约）：
- `streamV3.test.ts`：谓词用例去掉 SUSPENDED；原「SUSPENDED 结束进行态」用例**反转为**
  「SUSPENDED 不得定格 + 挂起期间增量仍应接受」。
- `streamV3Concurrency.test.ts` 场景3-5：**该用例原断言是错的**（`finalized: true`）。
  正确语义是「挂起不定格、增量继续收、恢复沿用同一回答组」。重构时注意：

## 第三轮 QA：撤销上轮的 SUSPENDED 语义误改 + 根代际守卫收窄（10-05 晚）

**上轮结论被推翻，本次是纠错，不是新增。**

### ① 上轮把 SUSPENDED 从终态谓词里删掉是错的（我改了设计契约去迎合自己的判断）

`docs/stream-protocol-v3-design.md` §8.1 逐字规定：**execution 的终态或 SUSPENDED，无论来自实时事件
还是 bootstrap，都通过同一状态转换结束相关响应的进行态**（路径 2），路径 4 要求定格后的迟到
STARTED/DELTA 不得复活响应。我上轮看到后端 `TERMINAL_THRESHOLD = COMPLETED` 就断言「SUSPENDED 不是终态」，
并把它从 `EXECUTION_TERMINAL_STATES` 删掉，还**反过来改旧测试**去迎合 —— 双重错误。

**真正的错**：一个谓词名 `resolveExecutionTerminal` 承担了两个语义。执行生命周期 ≠ 单个 streamKey 的响应生命周期。

正确修法是**拆谓词**（`src/utils/streamV3.ts`）：
- `resolveExecutionTerminal` = COMPLETED/FAILED/CANCELLED —— 只用于「本轮收尾了、要不要对账」
- `resolveResponseClosed` = 三终态 + SUSPENDED —— 用于「这段还能不能收增量」（`finalizeByExecution`）

三个调用点的归属：
| 调用点 | 用哪个 | 理由 |
|---|---|---|
| store bootstrap `executions[].status` → finalize | `resolveResponseClosed` | §8.1 路径 2 |
| store 实时 `EXECUTION_UPDATED` → finalize | `resolveResponseClosed` | 同上，两条路径必须等价 |
| `useChatView` D6 终态对账 watch | `resolveExecutionTerminal` | 挂起还会恢复，对账是白花查询 |

**教训**：谓词名出现「Terminal / Closed / Finished」混用时，先问「它答的是哪个问题」，再决定集合内容；
发现测试与新判断冲突时，**先查设计文档谁是权威**，不要先改测试。

### ② 全事件根代际守卫与 SESSION_UPDATED 生产口径冲突（真 bug，上轮引入）

### ① 新建 `frontend/src/services/sse.ts`（核心交付，重注释）

用户明说「不清楚前端 sse 怎么操作」，故文件头就是一篇说明：

- **传输层长什么样**：SSE = 长连接普通 HTTP 响应（`text/event-stream`），按 `\n\n` 切块，
  每块 `event:` 行给事件名、`data:` 行给 JSON 体 → 「解析 SSE」就是切块 + JSON.parse。
- **两种连法对照表**：原生 `EventSource`（GET-only、不能带自定义头、自动重连）vs

- **为什么发消息不能用 EventSource**：`POST /a/completion/stream` 是 multipart（含图片），
  EventSource 只能 GET 且无请求体 → 发送走 `readSseStream`，只有订阅 GET 端点才用 `openEventSource`。
- 本项目无鉴权（HC-1），不存在「EventSource 带不了 Authorization」的问题。

导出三个东西：`readSseStream(response, {onEvent, signal, onDone, onError})`、
`parseSseBlock(block)`（纯函数，可单测）、`openEventSource(path, {handlers, onAnyEvent, ...})`。

⚠️ **踩坑**：函数 JSDoc 里写 `<pre>` 使用示例时，示例中的 `/* ... */` 注释**会提前关闭外层块注释** →
`vue-tsc` 报一堆 `TS1128/TS1109/TS1161`。示例里的注释一律改成 `//` 或 `console.log`，别用块注释。

⚠️ **abort 要显式监听**：只把 signal 传给 fetch 不够 —— 响应头早已返回（流已建立），此后 abort
不会再让那个 fetch promise 拒绝。必须 `signal.addEventListener('abort', () => reader.cancel())`，
