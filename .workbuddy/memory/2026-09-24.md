## DSML 工具调用解析排查（23:00）——**不是框架侧解析问题**

**用户贴的原始输出**：
```
<|DSML|function_calls>
<|DSML|invoke name="execute_command">
<|DSML|parameter name="command" string="true">pwd && ls -la</|DSML|parameter>
</|DSML|invoke>
</|DSML|function_calls>
```

**取证链（自下而上，逐层排除）**：
1. **全框架搜 `DSML`/`invoke name`/`antml` → 零命中**。框架（含 1.0.2/1.0.3/1.1.0 全版本）**根本没有 DSML 相关代码**。
2. **应用侧搜 `DSML` → 零命中**。
3. `MessageCodecAdapter.toChatResponseEntity`（harness-adapter-langchain4j）：
   ```java
   for (ToolExecutionRequest request : aiMessage.toolExecutionRequests()) { ... }
   ```
   **直接信任 langchain4j 已解析的 `toolExecutionRequests()`，从不检查 `aiMessage.text()` 里是否还嵌着工具调用标记**。
4. `OpenAiStreamingModelProvider` → `OpenAiStreamingChatModel`（langchain4j 官方 OpenAI 协议客户端，标准 `tools`/`tool_calls` JSON；→ `StreamingHandlerBridge.onCompleteResponse` → `toChatResponseEntity`。

**根因（框架无过错）**：DeepSeek 系模型的已知问题——**DSML（DeepSeek Markup Language）是模型自有的工具调用格式**，官方文档确认 `|DSML|` 是 tokenizer 保留 token。当使用 **native function calling**（OpenAI 协议 `tools` 字段）时，DeepSeek **有时仍吐原始 DSML 文本**而非标准 JSON `tool_calls`。Open WebUI 官方文档记载为 *"DeepSeek V3.2 Function Calling Issues"*，诱因：高 temperature、多轮（6-8+）对话、复杂多步（15-30 次调用）导致 schema drift。
**转换层不可靠**：推理网关（VertexAI/OpenRouter 等）会尝试拦截 DSML 转 OpenAI JSON，但在**流式 / 高温 / 高并发 / 多轮**下拦截不可靠。此处 `langchain4j` 就是那层转换——它没能拦到，于是 DSML 文本落进 `aiMessage.text()`，`toolExecutionRequests()` 为空 → 应用侧看到"模型没调用任何工具，只是说了段 XML"。

**结论**：`MessageCodecAdapter` 的行为**符合设计**（协议层就该信任解析结果），问题在模型输出不合协议。要修只能在**应用侧做防御性恢复解析**（框架不该为一个厂商的非标准格式背锅）。

**修复方向（待用户拍板）**：
- **(A) 应用侧 DSML 恢复**（推荐）：在 `toChatResponseEntity` 之后、进入 loop 之前加一层"若 `toolCalls` 为空且 `text` 匹配 DSML 模式 → 解析出 toolCall 并回填"。**难点在流式**：DSML 会被切成 `["<","|DS","ML|in","voke"]` 跨 chunk，需要跨 chunk 状态机（缓冲 + 闭合检测 + schema 校验 + fail-closed）。
- **(B) 换模型**：agentic 场景改用 function calling 稳定的模型（Claude/GPT/Gemini 系）。
- **(C) 降 temperature + 限制多轮**：缓解而非根治。
- 注意 (A) 有个坑：用户 prompt 里若在讨论 DSML 语法，会误触发恢复——需"是否用户示例"的判定（ferstar 博客提到这点）。
� `ExecutionPersistenceRepository` 让业务侧从 DB 读的原因。
本次通过业务侧解码归一化绕开，未改动框架的 `copyOf`（设计意图不明，不擅动）。

## 过程暂停（流式中途中断）实现 —— 推翻上一节的局限

### 需求演进
上一节结论是"暂停只对多轮工具调用有效"，纯聊天任务因为只有一个 model 调用、
输出完就 `completed`，中间无检查点。
先尝试"无工具调用时再 check 一次信号" → 用户否决：
> "算了,如果是模型已经完成回复了再暂停,也没有意义了,我需要的是过程暂停"

即必须做到**模型流式输出过程中**就能中断，而不是等回复写完再补判。

### 实现原理
关键洞察：`DefaultStreamingModelInvoker.invoke()` 里
`handler.getStreamingResponseContext().future().join()` 是**唯一阻塞点**。
只要在流式回调的每个 chunk 处检查控制信号，命中即 `completeExceptionally`，
`join()` 立刻返回 —— 这就实现了非抢占式的中断。

### 框架侧改动（4 处 + 3 个新文件）
| 文件 | 改动 |
|---|---|
| `core/runtime/loop/suspension/ExecutionInterruptedException.java` | **新建**，携带 `Kind.SUSPEND`/`Kind.CANCEL` 的控制流异常 |
| `runtime/model/StreamingModelResponseBehaveDecider.java` | 新增 `control` 字段；`onPartialResponse`/`onPartialThinking` 开头调 `interruptIfRequested()`；`onFinalResponse` 改为 `complete(response)` 失败则丢弃；`onError` 开头 `if (future().isDone()) return;` |
| `runtime/model/ModelRequestFactory.java` | `build(Execution, List<String>)` → 增加 `ExecutionControlSignal control` 参数，透传给 handler |
| `runtime/loop/AgentLoopStepRunner.java` | `run()` 捕获 `ExecutionInterruptedException` 转 `LoopResult.suspended/cancelled`；`invokeModel(execution, control)` 解包异常 |

### ⭐ 关键坑：CompletableFuture 包装导致 catch 失效
第一版实测：流确实在 **0.28s 内被切断**（说明中断生效），
但终态落到 `FAILED(4)` 而非 `SUSPENDED(2)`。

日志证据：
```
java.util.concurrent.CompletionException: com.summit.core.runtime.loop.suspension.ExecutionInterruptedException: execution interrupted mid-stream: suspend
    at java.util.concurrent.CompletableFuture.reportJoin(CompletableFuture.java:413)
    at java.util.concurrent.CompletableFuture.join(CompletableFuture.java:2118)
    at com.summit.runtime.model.DefaultStreamingModelInvoker.invoke(DefaultStreamingModelInvoker.java:29)
```
根因：`CompletableFuture.join()` 抛出的是 **`CompletionException`（包装过）**，
`catch (ExecutionInterruptedException e)` 匹配不到 → 异常穿透到
`RuntimeProcessorTemplate.process()` 的 `catch (Exception)` → `onError()` → `FAILED`。

修复：`AgentLoopStepRunner.invokeModel()` 中增加 `findInterrupted(Throwable)`
沿 cause 链解包，只穿透 `CompletionException` / `ExecutionException` /
裸 `RuntimeException` 三种包装层，遇到其他异常立即停止 —— 
这样**真实的模型失败仍保持 FAILED 语义**，不会被误判成暂停。

### 最终验证（全部端到端实测通过）
| 场景 | 结果 |
|---|---|
| 纯聊天流式中途 suspend | 0.32s 切断，`RUNNING(1)` → **`SUSPENDED(2)`**，事件流无 `EXECUTION_FAILED` |
| 纯聊天流式中途 stop | 0.26s 切断，`RUNNING(1)` → **`CANCELLED(5)`**，以 `EXECUTION_CANCELLED` 收尾 |
| 多轮工具 suspend→resume（回归）| `SUSPENDED(2)` → `COMPLETED(3)`，快照 2625 → 15949 |
| 多轮工具 stop（回归）| `CANCELLED(5)`，以 `EXECUTION_CANCELLED` 收尾 |

框架侧测试 37 个全绿（`AgentLoopStepRunnerIntentionTest` 7 → 9，
新增 `unwrapsCompletableFutureWrappingAroundAnInterruptedStream`、
`keepsReportingGenuineModelFailuresAsFailures`）。

## 修复启动循环依赖（应用侧，13:00 前后）

**症状**：`APPLICATION FAILED TO START`，报 bean 循环。

**根因（关键是框架 `executionControl` 的形参类型）**：
框架 `AgentConfiguration.executionControl(ChatAgent agent, ExecutionRepository repo)`
形参是 **`ChatAgent`**，容器注入应用侧 `@Primary` 的 `IChatAgent`。
于是凡是**在构造期**需要 `ExecutionControl` 的 bean，都会被拖进
`IChatAgent → defaultRuntimeFactory → …` 这条链里，形成闭环。

实际暴露过**两条**环路（改掉第一条后第二条才浮出来）：
1. `IChatAgent → defaultRuntimeFactory → conversationManager → planContextAttachment
   → interactionServiceImpl → executionControl → IChatAgent`
2. `IChatAgent → defaultRuntimeFactory → defaultToolExecutionManager → toolRegistry
   → createPlanToolToolDefinition → createPlanTool → interactionServiceImpl
   → executionControl → IChatAgent`

两条环的**公共汇聚点都是 `interactionServiceImpl`**。

**最终修复（两处，均不改变行为）**：

| 文件 | 改动 | 作用 |
|---|---|---|
| `shared/config/workflow/LingXiPlanConfig.java` | `planContextAttachment` 参数由 `InteractionService` 改为 `InteractionRepository`，并自带渲染逻辑 | 断开环 1（附件只读，仓储不持有 `ExecutionControl`） |
| `interaction/application/service/impl/InteractionServiceImpl.java` | `ExecutionControl` 改为 `ObjectProvider<ExecutionControl>`，调用处 `.getObject()` | 断开环 2（延迟取用，构造期不再触发 `IChatAgent` 创建） |

`planContextAttachment` 的载荷改为 `description + "\n\n" + meta`（与原先 `InteractionVO::toString`
实际语义一致：正文在 `description`，任务清单在 `meta`），并避免把 id/状态/时间戳等运行期元信息喂给模型。

**验证**：`Started LingXiApplication in 6.4 seconds`，日志中 `circular|cycle` 出现 **0** 次。
唯一告警仍是已知的 jtokkit 不认识 `deepseek-v4-flash`。

**结论性经验**：
> 应用侧任何 bean 都**不要**在构造期直接注入 `ExecutionControl`（或 `IChatAgent`）。
> 必须用 `ObjectProvider` / `@Lazy` 延迟化，否则必然撞上上述环。

## decide() 决策写入上下文 + 审批路由接线（13:40 前后）

### 需求
`InteractionServiceImpl.decide(text, interactionId, isAllowed, sessionId)` 要把用户决策写进模型上下文。
改造前 `text` 与 `isAllowed` **两个参数在方法体里完全未被使用**，等于决策从未落上下文。

### ⭐ 核心契约：顺序不可调换（先改消息，再 resume）
`ExecutionControl.resume(String)` 内部是 `repository.findById(id)` → `agent.execute(execution)`，
而 `LocalExecutionRepository.findById` 内存命中时返回的是
**`snapshots.decode(snapshots.encode(cached))` 得到的副本**，不是 loop 正在用的那个对象。

> **resume 之后再改 `execution.getMessages()` 是无效的**——loop 已经拿着副本跑完了。

正确顺序（也是 `decide()` 现在的实现）：
```java
Execution execution = executionRepository.findById(executionId).orElseThrow(...);
appendDecision(execution, interaction, isAllowed, text);   // 先追加
Execution resumed = control.resume(execution);             // 再恢复（用 resume(Execution) 重载！）
modelContextService.replace(sessionId, resumed.getMessages());
```
`resume(Execution)` 是 `ExecutionControl` 上现成的重载（`DefaultExecutionController:30`），
能把我们改好的那个实例直接交给 loop。**不要用 `resume(String)`**。

### 决策消息形态（按用户选择）
- 类型 **`SYSTEM`**（与框架 `SUSPENDED_CONTEXT_MESSAGE` 同风格）
- `text` 作为**决策理由**附在结论之后
- **拒绝同样 resume**，由模型自行决定重新规划还是收手；消息只陈述事实，不替模型下指令

渲染正文（`renderDecision`）：
```
The user has APPROVED|REJECTED the plan "<title>".
The user's reason: <text>          ← 仅当 text 非空
Continue the task accordingly.
```

### 新增依赖（不重新引入循环依赖）
`decide()` 需要拿到 `Execution`，但 `ExecutionControl` 接口**没有 `findById`**。
故新增 `ObjectProvider<ExecutionRepository>`（`LocalExecutionRepository` 已实现该接口）。
`ExecutionRepository` 不依赖 `IChatAgent`，与构造期注入 `ExecutionControl` 是两回事——**但同样用 `ObjectProvider` 延迟取用**，
理由见 MEMORY.md 的循环依赖契约。

## ExecutionIdentity 反查逻辑优化方案（19:10，待用户选定）

病灶定性：**框架在失败时把 Execution 身份吞掉了**（调用方只知道"有异常"，不知道哪个执行失败），
"会话→最近执行"反查只是补救。候选方案：
- **B-lite**（零框架改动）：监听执行终态事件（payload 自带 executionId）精确回写；仍解码快照，需验证事件与快照落库时序。
- **B**（推荐，框架小改）：框架在 FAILED/CANCELLED 终态持久化快照处回调新 SPI（如 ExecutionTerminalListener.onTerminal(Execution, State)），应用直接拿内存 Execution replace——零反查零解码，覆盖取消场景。
- **C**：失败异常携带 Execution——包装（CompletionException）后易丢，反模式，不推荐。
- **D**（表结构更改，长期演进）：新表 execution_message(execution_id, seq, role, content) 随 addMessage 流式落库作消息单一真源，session_context 退化为视图或砍掉；根治"终态才落库"丢失窗口，但 compaction 需范围重写，改动最大。

### 19:15 用户质疑"这不是能拿到 executionId 吗" → 层次取证

- **executePrepared 层拿不到**：`execution = orchestrator.executeXxx(...)` 赋值语句抛异常即未赋值（catch 里读它连编译都不过）；异常也不带身份——框架最深处 `RuntimeProcessorTemplate.process` catch 是 `throw new RuntimeException(e)`，仅剩 cause 链。
- **orchestrator 层也拿不到**：入参是 AgentRequest，Execution 在框架 `ChatAgent.execute` L44 `ExecutionCreator.create()` 才诞生（雪花 ID 在此生成）。
- **但框架失败路径握着完整 Execution，两个应用可达出口（均零框架改动）**：
  1. **RuntimeLifeStyleManager.onError(Execution, Exception)**（推荐）：process catch 首行同步调用，消息全量、状态刚置 FAILED、早于 finally 的 save/unregister；框架装配 `ExecutionRuntimeConfig.runtimeLifeStyleListener` 标 `@ConditionalOnMissingBean`，应用声明装饰器 bean 即可覆盖。onError 里 `ExecutionIdentity.sessionId(execution)`（走 attributes，零查库）+ 内存 messages 直接 replace。

- CANCELLED 不走 onError（正常返回路径，executePrepared 的 replace 本来就会执行），无需处理。
- 落地（待用户确认）：RecoveringRuntimeLifeStyleManager 装饰 DefaultRuntimeLifeStyleManager，onError 恢复后委托；删除 latestExecutionId + recoverContextAfterFailure。依赖链 装饰器→ModelContextService→mapper 不回指 agent 链，无循环依赖。

### 19:26 澄清"调框架顺序能否解决" + 装饰器落地（用户确认"行,那就加一个装饰器吧"）
