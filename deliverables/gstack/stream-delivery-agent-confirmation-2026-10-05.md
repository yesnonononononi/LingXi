## 2. 本轮新增补测：4 条，2 通过、2 失败

文件：`frontend/tests/streamV3DeliveryFollowupAudit.test.ts`。未加入默认门禁，留作下一轮修复验收。

### F1：溢出仅作废 token，没有主动恢复（失败，P1）

`streamV3Store.stage` 溢出后调用 `abortSync`，这一半修复正确：旧 bootstrap 被拒绝，phase 留在 idle。

但 `streamV3Sync.scheduleRecovery` 只由 bootstrap 的失败结果/异常分支调用。store 溢出没有把失败信号通知协调器；协调器仍先记录 bootstrappedConnectionId、清退避计数，再调用返回 void 的 applyBootstrap。applyBootstrap 拒绝旧 token 后，协调器不知道没有应用成功。

真实 SSE 测试确认：溢出 → 旧快照返回被拒绝 → 无 1/2/4 秒恢复任务 → 没有第二次 bootstrap。

补测刻意排除了 SSE 收帧时刷新的长周期空闲定时器。它不是同步恢复；把“登记了任意定时器”当作恢复成功会得到假阳性。

**后续要求**：统一同步失败出口，将溢出状态明确传到协调器；只有快照被当前 token 接纳才记录同步成功。验收必须执行退避回调，观察第二次 bootstrap 和最终 live，同时验证切走取消恢复、旧请求不得回写。

### F2：未知 streamKey 的旧代际增量仍能复活（失败，P1）

`applyHistoryInvalidated` 对失效帧自身比较 revision，修复了旧失效帧回退和同值重复清快照。

但是普通 delta 路径仍未按事件的 historyRevision 检查有效性。墓碑只保护 store 已见过的 streamKey。

真实 SSE 补测：先推进到 rev=2 并作废 t1/e1，再推 rev=1、相同已作废轮次/执行、此前未见过的 streamKey。ensureResponse 创建新槽，旧正文被接纳。

**后续要求**：在新建/修改响应前校验根代际和已作废身份，不只依赖旧 streamKey 的墓碑。覆盖 STARTED、TEXT/THINKING、FINALIZED、COMMITTED 等入口；无 revision 的旧兼容事实要有明确规则，不能一刀切丢 USER 行。

### 已通过的两条

- bootstrap 失败后，执行已登记退避，重新请求并完成同步至 live。
- A 发起命令等待受理时切 B，B 的 v3 权威态为 IDLE，发送守卫没有继续被 A 阻塞。

这些是对报告的补充确认，不应把已确认通过的职责继续列为旧缺陷。

## 3. 不能统称为产品决策的工程缺口

原报告明确承认以下项未修改，本轮源码也仍能确认其存在。

| 缺口 | 性质 | 推进要求 |
|---|---|---|
| 卡片决断完成缺 v3 广播 | 原卡片实时状态合同的工程缺口 | TOOL 已提交事实携带完整 DTO 与根身份直投，审批客户端回执更新不能代替其他客户端的实时通知 |
| 普通工具结果未正确上实时通道 | 工具执行展示的工程缺口 | TOOL 行 text 是工具 id，不能按 Message JSON 解码；复用已知已提交工具事实，不逐卡回查 |
| ContextUpdate 默认写进 EXECUTION_UPDATED | 事件语义错误 | 显式列举执行生命周期，非生命周期不能覆盖 execution.status；实时上下文指标是否本批交付可单独确认 |
| v2 观察者仍查询、维护旧投影 | 迁移收尾与成本缺口 | 决定旧协议是否仍需兼容；纯 v3 路径不能为了无人消费的投影继续查库，不能用缓存缓解 |

这些项并非“没有失败反例，所以只是产品决策”。“尚未补用例”和“需求是否需要”是两个问题。至少卡片决断最终状态与普通工具结果属于原实时渲染链路，必须补生产者和回归。

真正需要明确产品边界的是：**切走期间未落库的 token，切回是否必须立即完整恢复**。当前无事件回放的设计只能接未来片段，完整正文需等定稿/落库。如果接受该边界，写入验收说明；若不接受，再设计独立能力，不用高频补查或缓存偷偷代替需求。
