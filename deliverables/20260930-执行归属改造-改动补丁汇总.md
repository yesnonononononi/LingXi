### P1　`execution` 建表脚本与 `ExecutionPO` 严重漂移 → 重写 init.sql 的 execution DDL
- **为什么必须补**：真库只有 6 列（`id / session_id / status / snapshot / created_at / updated_at`），而 `init.sql` 里是 14 列的**历史草稿**（`workspace_id` / `worker_id` / `lease_until` / `desired_action` / `version` / `max_steps` / `error_message` …）。新库按 init.sql 建出来的表与真库**不是同一张表**。
- **补在哪**：`init.sql` 的 `execution` 建表段（重写为「真库 6 列 + 8 个新摘要列」）；`src/test/resources/execution-status-schema.sql` 同步。
- **代价**：删掉了草稿里的 14 个列。已核实全仓 Java / XML / 前端零引用，且真库本来就没有 —— 但这是**替框架还历史债**，不是我引入的。
- **框架侧根治**：框架自己维护一份权威 DDL，业务只跑迁移。

### P2　模型展示信息不是框架一等公民 → 只能从连接配置里反解
- **为什么必须补**：`Execution` 没有 `modelName` / `provider` 字段。要落「执行时实际用的模型名快照」，只能从 `execution.getAgentRequest().getModelConfig()` 里读 `getModelName()` / `getProvider()`。
- **补在哪**：`LocalExecutionRepository#applySummary`（`LocalExecutionRepository.java:112-140` 附近）。
- **代价**：业务侧要理解框架 `ModelConfig` 的内部结构；且 `ModelConfig` 里同时躺着 `apiKey`（见 §8），语义上是「连接配置」而非「展示元数据」，从它取展示字段属于**跨界取用**。
- **框架侧根治**：`Execution` 增加 `modelName` / `provider` 一等字段（或在完成事件里带上），业务不必反解。

### P3　`startAt` 的「首次开始」语义是巧合可用，不是契约
- **为什么算补丁**：`Execution.start()` 设 `startAt`，`resume()` **不重设** —— 这刚好等于「首次开始时间，恢复不重置」的业务口径。但它没有被文档化成契约。
- **补在哪**：`LocalExecutionRepository#applySummary` 直接把 `execution.getStartAt()` 写进 `started_at`，并在注释里写明「恢复不重置」。
- **代价**：**框架哪天让 `resume()` 重设 `startAt`，总历时会静默变短，且没有任何测试会红**（业务测试断言的是业务侧行为，不是框架契约）。
- **框架侧根治**：把 `firstStartedAt` 与 `lastResumedAt` 分开显式表达。

### P4　父子执行关系只存在于业务自塞的 attributes 里
- **为什么必须补**：`root_execution_id` 的唯一来源是 `attributes["lingxi.root_execution_id"]`（业务在委派时自己塞的字符串属性），框架 `Execution` 没有父子字段。
- **补在哪**：`LocalExecutionRepository#applySummary` 用 `ExecutionAttributes.readLong(attributes, ROOT_EXECUTION_ID)` 反解。
- **代价**：属性是 `Map<String,Object>`，JSON 往返后可能是 String 也可能是数值 —— 必须用统一的读取函数（`readLong`）才不出错。这层「弱类型桥」是纯补丁。
- **框架侧根治**：`Execution` 增加 `parentExecutionId`。

### P5　状态机 ↔ 数字码的映射在 5 处重复维护
- **为什么算补丁**：框架 `ExecutionState` 枚举与 `execution.status` tinyint 之间没有官方映射，只能手写 `switch` / 常量。当前重复点：
  1. `LocalExecutionRepository.java:291-292`（枚举 → 码）
  2. `ExecutionQueryServiceImpl.java:43-47`（码 → 枚举）
  3. `ExecutionIdentity.java:23-25`（常量 0/1/2）
  4. `ExecutionRepositoryImpl.java:26-28`（常量 0/1/4）
  5. `ExecutionRegistrationServiceImpl.java:17`（常量 0）
- **本次新增的**：第 4、5 处（因为要新增 `markFailedIfUnfinished` 与预插）。**是本次把重复从 3 处推到了 5 处。**
- **代价**：加一种状态要改 5 个文件；漏一处就是静默错判（例如把 SUSPENDED 误标 FAILED，用户再也恢复不了）。
- **框架侧根治**：`ExecutionState.code()` / `ExecutionState.of(int)` 官方映射。

### P6　`executionId` 的双口径（框架 String ↔ 业务 BIGINT）
- **为什么必须补**：框架全程用 `String executionId`；业务主键是 `BIGINT`。每一个跨边界点都要转一次。
- **补在哪**：
  - `ExecutionIdentity#numericOrNull(String)`（本次新增的工具方法，失败返回 null 而不是抛异常，用于「观测落库不得拖垮主链路」的场景）；
  - `ConversationTranscriptService` 的 4 个方法全部增加 `Long executionId` 形参；
  - `DatabaseConversationTranscriptSink` / `ExecutionErrorTranscriptListener` / `CallSubAgentTool` 三处调用点各转一次。
- **代价**：一次执行要写四类行（USER / AI / TOOL / ERROR），而**框架只回调 AI/TOOL 那一类**（`ConversationTranscriptSink#appendRound`），USER 与 ERROR 得业务自己写 —— 于是「同一个 executionId 贯穿四类行」被拆成两条路径，形参要一路加到底。
- **框架侧根治**：框架把 executionId 定为 `Long`（或业务全程用 String 主键）。

### P7　预插执行行 —— 对框架 `save()` 条件插入语义的适配 ★最脆弱
- **为什么必须补**：计划要求「生成 executionId → **保存初始执行** → 与用户消息关联 → 启动执行」。而框架 `LocalExecutionRepository.save()` **只在「状态 CREATED 且该行不存在」时 insert**，其余走条件 update。要让用户消息落库时就有一条 execution 行，业务只能自己先 insert。
- **补在哪**：新增 `ExecutionRegistrationService` + `ExecutionRegistrationServiceImpl`（**第二个 execution 写路径**）；在 `RequestPreparer#commitUserMessage`（`@Transactional`）里与用户消息同事务提交。
- **代价（这是本次最值得讨论的一处）**：
  - 依赖一个**隐式的框架实现细节**：框架首次 `save` 会因为「行已存在」而落到 update 分支。框架若改成 `INSERT ... ON DUPLICATE KEY`、或在 CREATED 时断言行不存在，就会破 —— **且破的方式是「所有聊天都写不进去」，不是局部降级**。
  - 业务侧因此出现了**两个 execution 写点**（框架的 `LocalExecutionRepository.save` + 业务的 `ExecutionRegistrationServiceImpl`），职责边界变模糊。
  - 它是 P8 的**直接原因**。
- **框架侧根治**：把「执行注册」变成框架一等能力（例如 `ExecutionRepository.register(request)` 返回 executionId 并自行建行），业务就不需要第二条写路径。
- **可选的简化方案**：**不预插**。代价是「只有 USER、没有 AI 回复的失败执行」在历史里查不到 execution 行 → 状态不可见（计划第 9 条验收明确要求可见）。若接受这条降级，可同时删掉 P7 与 P8。

### P8　启动失败收口 —— P7 的衍生补丁
- **为什么必须补**：预插带来副作用 —— 执行若在框架 loop 起来之前就失败（Agent 解析不到、模型配置缺失），行会**永久停在 CREATED**，历史里出现一条「永远创建中、既无回复也无失败提示」的记录。
- **补在哪**（四层透传，为一个条件更新）：
  1. `ExecutionMapper#markFailedIfUnfinished`（带状态条件的 UPDATE）
  2. `ExecutionRepository#markFailedIfUnfinished`
  3. `ExecutionRepositoryImpl` 实现
  4. `ExecutionRegistrationService#markStartupFailed` + `ChatServiceImpl` 的 catch 分支
- **代价**：一个「收口」动作要穿四层。若不预插（放弃 P7），这一整套都不需要 —— 框架自己会把终态写掉。
- **安全边界**：条件更新只命中 CREATED / RUNNING；SUSPENDED 与已终态**绝不触碰**（误标失败会让「待恢复」入口消失）。已由 `ExecutionStartupFailureClosureTest` 钉住。
