# 响应流演进方案

目标不变：文本按 offset 持续打印，完整响应和历史查询写入同一份展示状态，最终以可回放日志替换 TURN_SNAPSHOT 对账。

## 本次调整

- responseId、文本／思考各自的 offset、工具 requestIndex 均由框架提供，业务只消费位置，不分配序号或缓存工具位置。
- 完整 AgentMessageEvent 在模型拦截器之后、工具执行之前发出；业务直接依据完整工具列表确定 placement。用途随完整响应和历史投影返回，不需要额外的 RESPONSE_RESOLVED 事件。
- 用途未确认时在过程区逐段打印，不提前标记 PROCESS；只有明确 BODY 才进入正文，确认 PROCESS 时保留原文本节点。
- 同一 execution 内按整数 responseId 排响应；响应内依次展示思考、文本、按 requestIndex 排列的工具。不同轮次仍按业务轮次顺序排列。
- 不兼容旧 UUID、responseOrder 或缺少模型响应身份的数据，不做旧会话数据迁移。

## 已完成

增量保持框架 offset，全文从零偏移合并；实时工具立即展示；实时和历史共用响应位置与用途规则。响应缓存和专用推送拦截器已删除。

## 后续顺序

1. 将剩余块更新、历史回填统一成响应内容与工具状态的写入入口，继续使用当前流式传输，保持即时打印。
2. 增加可回放事件日志和后端单调 seq，统一回放与实时订阅，替换 TURN_SNAPSHOT 对账。responseId 只排序响应，不能代替事件游标。
3. 再处理进行中日志保留、轮次完成后的压缩与失败响应收尾。

验证以实际展示和幂等结果为准。重放、重复或乱序文本必须收敛；截断造成缺失的事件需补齐后再比较终态。
