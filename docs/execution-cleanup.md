# 无用执行数据清理

设置 → 数据管理中的「清理无用执行数据」先读取预计条数，再通过 POST 执行清理；完成后展示实际删除与剩余条数。预览结果只供展示，删除时重新检查版本、状态与引用。

可清理对象必须同时满足：

- execution 已处于 COMPLETED、FAILED 或 CANCELLED。
- 没有属于现存会话的 chat_turn 引用。
- 没有 tool_call、execution_resume_task 或 task 引用；这些引用无论自身状态如何都保留。
- 执行的进程内控制槽位已释放。

已删除会话留下的孤立轮次不会阻止回收；重发回滚后失去轮次引用的执行也可回收。入口只删除 execution 行，不级联修改其他模块记录。

有效历史重发所需的检查点是按**目标轮次自己的 executionId** 保护的：只要那一轮的 chat_turn 还在、会话还在，它的正文文件就不会被清理，不会因为同会话后面又跑了几轮而失效。CREATED、RUNNING、SUSPENDED 及未知状态均不在回收范围内。

## 检查点正文文件同样被回收

正文不在数据库里：`execution.snapshot_file` 只是文件标识，正文在 `<数据目录>/checkpoints/<executionId>/<fileId>.json`。
同一个清理入口因此还要处理三类文件垃圾，否则数据库行删掉了、几百 MB 的正文还躺在磁盘上：

1. 被回收执行的正文文件；
2. 提交后删除失败留下的旧文件（`snapshot_file` 已经不指向它）；
3. 未完成的临时文件（`*.part`）与数据库行已消失的孤儿文件。

顺序是**先提交数据库删除，再删对应文件**：库是唯一权威。反过来先删文件再删行，一旦删行失败，库里就会留下一条指向不存在正文的执行。现在的最坏情况是「行没了、文件还在」，那只是垃圾，由下一次清理兜底。

约束：

- 文件删除与执行正文读取按 `executionId` 互斥（同一把门闩），保护「已查到引用、尚未打开文件」的窗口；删不掉或仍在写入时跳过，不影响已提交的删除结果。
- 存储侧的在途登记（写入 → 发布 → 事务定论）还在的文件一律不删。
- 文件枚举按批进行，严格限定在 `<数据目录>/checkpoints` 根目录下的执行子目录内，只读文件名不读正文，不递归处理数据目录里的其它内容（`images`、`skill`、配置文件等一律不碰）。

接口：

- GET `/execution/cleanup/preview`：`executionCount`。
- POST `/execution/cleanup`：`deletedCount`、`remainingCount`。

计数按后端统一 JSON 规则返回十进制字符串。清理每批最多 200 条候选，单次事务最多扫描 10,000 条；单次请求最多扫 400 个执行目录、每个目录最多处理 50 个文件。仍有候选时可再次清理。过程中失败则整次回滚，并发清理按实际删除行数计数。

删除释放的是数据库内部可复用空间，不承诺 SQLite 文件立即缩小（需要时用 `VACUUM`）。该入口也不删除外部备份、图片或配置文件。
