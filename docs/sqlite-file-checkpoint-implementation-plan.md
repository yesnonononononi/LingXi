# SQLite 与文件检查点实施方案

## 目标与范围

目标是在维持现有业务语义的前提下，显著降低执行保存、恢复时的堆内存峰值和 OOM 频率。采用 SQLite 保存业务记录与执行摘要，执行检查点正文以未压缩 UTF-8 JSON 文件保存。

本方案按新建 SQLite 数据库、不兼容旧 H2 数据设计。旧库和现有诊断备份保留，不自动删除或改写；安装目录之外的现有 JSON 配置继续沿用。

范围限定：

- 不加压缩、OOM 熔断、自动重启、自愈流程、常驻监控或新的崩溃恢复状态机。
- 不改 Agent 框架核心接口和 Execution JSON 语义，不修改本机框架仓。
- 不新增通用存储框架、多数据源路由、异步写入队列或跨资源事务框架。
- 复用设置页现有“清理无用执行数据”，不新增主动破坏历史重发能力的清理模式。
- 文件完整发布、数据库事务及提交后删除属于基本持久化正确性，保留这些必要约束。

当前实验已经复现 H2 行版本、撤销记录、写盘缓冲区与应用副本共同造成的内存放大；尚未完整重放当日全部业务时序。本方案的效果以改造前后同负载对照为准。

## 最终存储结构

```text
<lingxi.data.dir>/
  lingxi.sqlite
  lingxi.sqlite-wal / lingxi.sqlite-shm   # 由 SQLite 管理
  checkpoints/
    <executionId>/
      <唯一文件标识>.json
```

数据库 `execution` 保留现有 id、session_id、状态、version、resume_generation 和时间字段，将 snapshot 正文替换为文件相对标识。文件标识只是存储定位信息，不能替换 executionId、sessionId 或 turnId。

每个 execution 只保留一份当前已提交检查点；保存过程中允许旧文件与待提交新文件短暂共存。历史轮次对应的 execution 仍保留自己的检查点，不能按会话只留最后一轮。

## 一、切换 SQLite

改动入口：`pom.xml`、`application.yaml`、`MybatisPlusConfig`、初始化脚本与数据库初始化器，以及包含数据库专用 SQL 的 Mapper/仓储。

1. 选择并固定经过验证的 sqlite-jdbc 版本，检查其 SQLite 内核版本和 Windows 打包运行情况；生产包移除 H2 依赖。
2. SQLite 使用独立文件名，不复用 `.mv.db`；MyBatis-Plus 分页方言改为 SQLite。
3. 使用 SQLite 专用新库建表脚本和简单版本化初始化，退出原 H2 补列流程，不保留运行时双库兼容分支。
4. 适配 AUTO_INCREMENT、ENUM、ON UPDATE 时间、字段类型、默认值、索引、注释语法和数据库元数据查询。雪花 ID 及前后端字符串 ID 契约不变。
5. 逐个替换 FOR UPDATE 的并发语义，使用短事务、原子条件更新和已有版本/唯一约束，不能只删除 SQL 尾句。重点覆盖消息追加、checklist、邮箱和恢复任务。
6. 检查 REQUIRES_NEW：外层已经写库时，不允许再等待新连接开启嵌套写事务。优先把既有独立配置冻结安排到外层写入之前，保持配置版本语义。
7. 以 WAL、synchronous=FULL、有限 busy_timeout 为初始验证配置，连接池保持小规模。写事务的锁取得方式先用真实 Spring 事务与竞争用例验证，不在 Mapper 中自行拼接 BEGIN/COMMIT。

业务持久化继续使用领域仓储接口、PO、BaseMapper 和 AbstractRepository。自定义 SQL 集中在 Mapper/XML，初始化交给脚本执行器，不新增手写 JDBC 仓储。

先通过 SQLite 原型门槛：建库、分页、雪花 ID、时间类型、乐观版本竞争、重复消息追加、嵌套事务和 Windows JNI 加载。原型不通过时先解决适配，不推进文件快照以掩盖问题。

## 二、执行检查点流式读写

主要调整现有 `LocalExecutionRepository`、`ExecutionCheckpointService`、`ExecutionSnapshotReader`、执行领域模型/PO/仓储和快照查询接口。

新增一个业务侧检查点存储端口及本地文件实现，将文件命名、路径校验、流式 JSON、临时文件发布和删除集中在这里；复用现有读取器、事务回调和 executionId 协调锁，不把文件操作分散到恢复、审批、重发等入口。

保存顺序：

1. 使用独立临时文件，通过 ObjectMapper.writeValue(OutputStream, execution) 流式输出；不经过 writeValueAsString、完整 byte[] 或 JsonNode 树。
2. 关闭并刷盘后，在同一文件系统内原子发布为新的独立 JSON 文件，不覆盖旧文件。
3. 通过现有领域方法和版本条件更新，将新文件标识、执行状态和恢复代际同事务提交。
4. 提交后删除旧文件；回滚时删除本次未提交的新文件。删除失败留待手动清理，不把已经提交的保存伪报成失败。

读取顺序：

- 根据数据库权威引用打开文件，在流的有效期内完成反序列化并关闭；每次返回独立可变的 Execution。
- 去掉完整 JSON 字符串检查点缓存，保留运行控制信号注册表；先依赖文件系统缓存，不新增应用级正文缓存。
- 读取与文件回收按 executionId 协调，保护“已查到旧引用、尚未打开文件”的窗口；清理跳过未完成的写入。
- 文件不存在或无法解析时明确失败，不静默改读旧版本。

框架 `ExecutionRepository.save/findById/afterCommit` 保持不变。流式读取消除中间正文副本，最终 Execution 对象本身仍需要驻留堆内存。

## 三、保持现有业务语义

所有执行快照读取统一经过文件适配，删除 `findSnapshotById` 返回整段 String 的内部契约。

- 暂停、补充恢复、审批恢复、根执行与子执行仍定位原 executionId，不更换业务身份。
- 历史重发从目标轮次自己的检查点读取基线，保持当前行为；不在本轮重构基线算法。
- 保持 version 条件更新、resume_generation、终态保护、提交后通知顺序。
- 取消旧 H2 正文和旧格式快照的读取兼容，不顺带重构模型请求、图片表示或框架消息对象。

## 四、减少会话上下文更新的无用读取

`session_context.content` 本轮仍留在 SQLite，不扩展第二套文件存储。

现有 `ModelContextService.replace` 在覆盖正文前调用 findById，将旧正文也完整加载，只用于判断行存在及取得元信息。新增轻量摘要查询，只读取 sessionId、version 和必要时间字段，再通过领域方法更新新正文。

这一单元仅减少一次无用的大文本加载，不修改会话上下文语义，不引入缓存和新状态。新上下文序列化仍可能形成大字符串，必须计入整体压测结果。

## 五、复用手动清理与目录管理

扩展现有 `ExecutionCleanupService/ExecutionReclaimService`：

- 仍只清理无业务引用且已结束的执行；先提交数据库删除，再删除对应检查点文件。
- 保护运行、挂起、审批、后台任务和有效历史重发所需检查点。
- 在同一清理入口回收失败删除留下的旧文件、无引用文件和未完成临时文件；使用存储实现内的写入登记/现有锁避免删除在途文件，不建立新的业务回收状态机。
- 文件枚举按批进行，限定检查点根目录，不读取正文、不递归删除用户数据目录。
- 前端继续使用现有清理按钮与接口，必要时只改说明文案，不新增清理功能页或模式。

现有数据目录迁移和开发初始化脚本需要将 SQLite 与 checkpoints 作为一个数据集合处理。SQLite 的一致性备份通过集中维护 Mapper/驱动支持的备份能力完成，不复制正在写入的主文件作为备份；迁移窗口排除检查点写入，复用已有迁移和重启流程，不新增通用在线迁移服务。

## 实施顺序与提交边界

| 顺序 | 独立提交单元 | 完成门槛 |
| --- | --- | --- |
| 1 | SQLite 驱动、初始化、分页与基础类型 | 新库启动及真实 SQLite 原型通过 |
| 2 | 业务 SQL、锁与事务适配 | 消息、checklist、邮箱、恢复任务竞争用例通过 |
| 3 | 文件检查点、元数据持久化和流式读取 | 文件与数据库提交/回滚正确，正文缓存移除 |
| 4 | 恢复和历史重发消费者适配 | 原业务回归通过，框架接口未改 |
| 5 | 上下文更新轻量查询 | 替换正文前不读取旧正文，行为保持 |
| 6 | 现有手动清理、目录迁移与脚本 | 引用保护、并发读取和整体搬迁通过 |
| 7 | 安装包与同负载内存验收 | 产物为 SQLite，压力指标达到目标 |

每个可独立评审的单元完成后立即提交；保留其他会话的在飞改动。只有数据库适配影响的集成测试切换到 SQLite 临时文件库，纯逻辑测试不做机械重写。

## 验证与效果验收

功能守卫：

- 保存后恢复语义一致；修改恢复副本不影响已提交检查点。
- 发布新文件后数据库回滚，旧检查点仍可读取；提交后只回收正确的旧文件。
- 暂停/补充恢复、审批、子执行唤醒、历史重发和终态保护保持现有语义。
- 手动清理与并发读取不误删，删除会话后按既有引用规则回收。
- Windows 下验证文件占用、文件发布、目录搬迁及 sqlite-jdbc 打包。
- 在测试进程中验证关键提交窗口被中断后可重新打开数据；不为生产增加额外恢复流程。

对本轮新增的缺陷守卫执行有行为差异的回退变异，确认断言会变红；扫描“无残留”前验证扫描器正对照与覆盖范围。

内存验收：使用固定版本夹具、相同 512 MiB 堆和相同保存频率，比较改造前后的单执行、并发保存、检查点加会话上下文写入。实验夹具若由丢失根快照重建，必须单独标记，不能冒充原现场。

- 固定负载连续多轮运行无 OOM，文件数随旧版本回收保持稳定。
- 记录峰值堆占用、GC 时间和保存/恢复耗时；将峰值堆占用下降至少 30% 作为本轮建议验收目标，不预先承诺结果。
- 堆中不再常驻整段执行 JSON 缓存，不再产生执行 JSON 的完整 String/JsonNode 中间副本。
- 如会话上下文或运行中对象仍使验收失败，报告实际瓶颈，再决定最小补充改动，不自动扩展成图片外置、消息分页或框架重构。

诊断参数只用于测试，不向安装版增加常驻监控。SQLite 原生内存与 JVM 堆分开观察，避免把 JVM 堆下降误报成进程总内存同比下降。

## 交付物

SQLite 新库初始化与业务适配、未压缩文件检查点存储、现有手动清理和目录迁移适配、回归/竞争/提交窗口测试、安装包验证记录与改造前后内存对照报告。

部署或替换安装包另行进行；本方案不包含修复旧坏库、迁移旧历史或删除旧数据。
