# 主执行取消后子会话假运行：排查与修复

## 现场事实

- 根会话 `2117251863052189696`，子会话 `2117254887128596480`。
- 2026-11-02 22:09:33（Asia/Taipei），子执行 `2117257503883558912` 记录“保存执行检查点失败”；同一时刻根执行 `2117257418252648448` 取消。
- 会话树、bootstrap、历史接口一致：根轮次已经 `CANCELLED`，子轮次仍为 `RUNNING`，最后一条子执行输出停在 22:09:22。
- 对 PID `50752` 获取含虚拟线程的 JSON 线程转储：已无该子执行的 loop / 委派线程。右侧“执行中”来自未收口的数据库状态，不代表仍有模型工作。
- 用户确认该轮点过停止按钮：主执行取消符合请求，缺陷在子执行取消收尾。
- “待处理输入已保留：执行已取消”由取消后的输入复查生成，是结果通知，不是取消原因。现有日志缺少停止请求入口记录，本次补上日志便于后续独立追查。

## 原因与范围

停止入口先发送框架取消信号，再直接 `interrupt()` 子执行线程。框架已经通过控制信号取消模型请求、工具等待及工具工作线程；额外打断 loop 线程可能正好破坏检查点落盘。

真实文件复现命中 `FileChannel.force()` 的 `ClosedByInterruptException`。真实 H2 文件库复现进一步证明，带中断标记的数据库访问也可能失败。现场旧日志仅保存异常摘要，未保留底层 cause，因此底层异常类型来自同路径复现，而非现场堆栈。

框架结束时先在内存改变执行状态，再保存检查点；保存失败会留下旧 `RUNNING` 行。异步兜底只处理 `CREATED` 执行，并发送“未能建立执行”通知，不能修复这类运行中断尾。原停止实现又只直接收口无控制槽位的 `SUSPENDED`，遗留运行态因此无法再次停止。

本次保持原模块、事务和 Mapper 分层：

1. 停止入口保留全会话树取消信号，移除对 loop 线程的额外中断，并记录停止请求身份。
2. 检查点使用 `FileOutputStream` 和 `FileDescriptor.sync()`，保留流式写入、同步落盘、原子发布、回滚清理。
3. 检查点保存、读取及提交后通知暂存已有中断标记，完成或抛错后恢复；业务取消信号始终保留在控制槽位。
4. 无控制槽位的遗留 `RUNNING` 与 `SUSPENDED` 都可直接取消；活跃执行仍交给原循环完成落盘和终态广播。
5. 异步子执行异常日志保留完整异常链。
