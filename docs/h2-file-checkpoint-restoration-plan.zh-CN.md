# H2 文件库恢复与现有数据迁移方案

日期：2026-10-31。状态：方案与历史审计完成，尚未实施数据库切换、数据迁移或安装版替换。

审计代码基线：`6e95230ab938f9c74d1f582dc87e24863aedb0d0`。工作树存在其他任务的未提交修改；本方案以已提交历史及当前存储契约为依据，实施前应重新确认基线，不覆盖其他任务的代码。

## 1. 结论与改造目标

可以恢复 H2，但应在当前代码上形成一组新的适配提交，不整体回退到切换 SQLite 之前。

目标结构是 **H2 文件库保存业务数据与执行摘要，现有文件存储继续保存检查点正文**。通过 H2 的多版本并发与行级锁，减少独立工具、会话和子执行之间因 SQLite 单写者限制产生的冲突；保留幂等、唯一索引、版本条件更新与恢复代际约束。同一条记录的竞争和事务死锁仍需处理，换库不代表不再需要并发控制。[H2 并发与连接说明](https://h2database.github.io/html/features.html)

本次改造包括数据库适配、当前 SQLite 数据迁移、目录管理与真实文件库验证，不修改框架仓，不迁移为 JSONL，不修改前端会话身份契约，不同时重构工具调度器。

本轮仅交付改造文档。下文的测试、迁移与发布步骤均为待实施工作，不是已经完成的验证结论。

## 3. 恢复 H2 必须先解决的历史问题

### 3.1 旧 H2 的内存与损坏证据

[安装版 H2 事故报告](qa/installed-h2-oom-root-cause-2026-10-30.md)记录了 H2 2.3.232 后台写盘 OOM、panic 后继续提交与缺块。首次现场没有堆转储，不能精确指认哪条业务数据导致该次 OOM。

[真实数据对照重放](qa/first-oom-desktop-pet-replay-2026-10-31.md)进一步在旧 H2 实现的受限堆场景复现内存耗尽，并观测到大字符串、页缓存、撤销记录与写缓冲扩容共同占用。旧版事故前单执行样本在 1 GiB 堆下虽然完成，采样峰值接近 989 MiB。这些结果对应旧实现，既不能忽略，也不能直接套用于“新 H2 + 文件检查点”。后者尚未经过同负载验证。

因此，不恢复 H2 2.3.232，不恢复 `execution.snapshot` 大 VARCHAR，不恢复整段检查点字符串缓存，不用扩大堆代替对照测试。

### 3.2 版本与大文本方案

候选版本固定为 **H2 2.5.252**，不依赖 Spring Boot 默认版本，也不使用浮动版本。该版本已有官方发布；历史独立 panic 探针对它取得了“panic 后停止推进”的结果，但这不等于新业务实现已经通过验收。[官方发布](https://github.com/h2database/h2database/releases/tag/version-2.5.252)

实施时对实际打包的 JAR 再验证版本、来源、哈希及 panic 防护。官方已合并 [PR #4343](https://github.com/h2database/h2database/pull/4343)，其中包含停止 panic 后继续保存 chunk 的修复。验证必须落到最终产物，不能只根据版本号大小推断。数据库发生致命存储故障后，应使本次应用实例停止受理新写入并明确失败，不靠连接池持续重连掩盖故障；具体接入点在实现阶段以探针确认，不扩展自动修库或自动重启系统。

`session_context.content` 仍可能很大，历史样本超过 1,000 万字符。新 H2 DDL 对无界正文明确使用 **CLOB**，同时审查 `session_message.content`、`tool_call` 的内容和输入输出、运行配置 payload、后台任务输出等实际大文本字段，不能沿用 MySQL 模式下把 LONGTEXT 映射成普通 VARCHAR 的旧假设。H2 官方说明 CLOB 的大值可流式处理，而 VARCHAR 会完整进入内存。[H2 大文本类型](https://h2database.github.io/html/datatypes.html#character_large_object)

业务模型暂时仍以 String 表示上下文；CLOB 只改善存储引擎路径，不能消除 Jackson 序列化和最终消息对象的内存占用。MyBatis-Plus 的 PO/Mapper 层按大文本列配置适当的 CLOB 处理，必要的 Reader/Writer 逻辑限定在 TypeHandler，验证返回业务层前不留下已关闭的 Clob/Reader。禁止为此新增手写 JDBC 仓储，不全局替换所有 String 的处理器。

## 4. 目标存储与约束

```text
<新的数据目录>/
  lingxi-h2.mv.db
  checkpoints/
    <executionId>/
      <snapshotFile>.json
```

H2 连接名建议为 `lingxi-h2`，对应文件 `lingxi-h2.mv.db`，避免误打开遗留的 `lingxi.mv.db`。生产仍使用文件库，不使用内存库。部署维持一个后端进程拥有该库；开发与安装版使用隔离目录，不为换库引入 AUTO_SERVER 或关闭文件锁。

| 数据 | 权威位置与保持的语义 |
| --- | --- |
| 会话、轮次、展示消息、工具状态、邮箱、恢复任务、清单、执行摘要 | H2；主键、唯一约束、版本、代际和关系不变 |
| 执行检查点正文 | 现有 JSON 文件；H2 的 `snapshot_file` 是唯一权威引用 |
| 当前模型上下文 | H2 CLOB；保留轻量摘要查询与整笔替换语义 |
| 设置、模型、提供方、MCP 等现有 JSON 配置 | 沿用当前配置仓储；不因旧 H2 曾有同名表就改变权威来源 |
| 图片与其他资源 | 沿用现有资源路径，数据搬迁时按实际引用一起校验 |

保存顺序保持“临时正文流式写入并刷盘 → 原子发布新文件 → 数据库提交引用 → 提交后回收旧文件”；回滚删除本次新文件。读、保存、清理继续按 executionId 协调；保留在途登记、清理游标和历史重发引用保护。

## 5. 生产代码改造清单

### 5.1 依赖、连接与异常

- `pom.xml`：固定候选 H2 版本；最终应用运行时移除 SQLite 驱动。迁移工具单独携带两个驱动，不引入常驻双数据源。
- `application.yaml`：改为 H2 文件连接与驱动；保留设置页解析 `lingxi.data.dir` 的契约。先维持小规模连接池，以实际并发结果调整，不直接恢复旧版 20 连接。
- `MybatisPlusConfig`：显式采用 `DbType.H2`。
- 退出 SQLite 专用异常翻译和时间处理注册，恢复适用于 H2 的 Spring 异常语义及时间映射；核对 MyBatis 自定义注册与包扫描两条路径。
- `TransactionRetryTemplate`：对 H2 实际死锁、锁超时建立精确分类；普通 SQL 错误、唯一键业务冲突和致命存储故障不作为一般锁冲突重放。保持有限次数和事务外重试，有外层事务时由外层拥有原子性。

时间转换必须保留现有 UTC 事实和毫秒精度。建议以显式 UTC 转换的 `TIMESTAMP(3)` 映射作为起点，分别验证 Instant 与 LocalDateTime；不得依赖机器时区或直接把本地时间文本当成另一个时区。数据库默认时间、更新时钟及排序行为一起验证。

### 5.2 DDL 与初始化

新增 H2 专用的版本化脚本，建议放在 `src/main/resources/db/h2/`。以**当前完整 schema 与 PO**为真源重建新 H2 基线，包含 `snapshot_file`、`reasoning_effort` 以及所有当前约束，不以旧 `init.sql` 作为完整真源。

初始化器可复用“版本号排序、脚本校验、启动前完成初始化”的思路，脚本交给现有脚本执行器执行。不能复制 SQLite 初始化器的“所有 DDL 都能事务回滚”承诺：H2 的多种 DDL 会提交当前事务。升级脚本需要幂等与失败后重入规则，版本完成标记只在对应步骤验证通过后登记；半途失败时停止业务启动，不记成成功。[H2 DDL 事务说明](https://h2database.github.io/html/commands.html#alter_table_add)

新库迁移先完成建表，再导入数据。SQLite `schema_version` 是源引擎的脚本执行记录，不能原样导入 H2 当作目标版本状态；另记源版本、迁移工具版本和数据清单。

H2 标识符大小写、保留字、数据库自增、NULL 唯一索引行为、状态值约束、时间默认值与自动更新时间逐项核对。当前 LIMIT/OFFSET、条件更新等 H2 可支持的写法保留，通过真实执行确认后再决定是否修改，避免为了“回滚”制造无关差异。

### 5.3 仓储、工具和事务

继续采用领域仓储接口、`RepositoryTemplate`、`AbstractRepository`、PO 与 BaseMapper。自定义 SQL 集中在 Mapper/XML，参数绑定；不新增 JDBC/JdbcTemplate 业务仓储。

保留 `2adbb9a` 带来的条件更新、唯一索引、清单协调及受理前冻结配置。不要批量补回 FOR UPDATE 或旧嵌套事务；仅在真实 H2 竞争用例证明当前语义缺口时做局部调整。

工具分类依据业务副作用，不依据“是否写观测记录”。read、搜索等可继续并发；其开始和结束同样要写 `tool_call`。选择、审批的原子结论与恢复登记必须正确，不能用全局串行工具执行掩盖持久化问题。当前框架在混合批次里只要一个工具要求串行就会串行整批，这次换库不顺带修改这个规则。

重点核对 `ToolCallRegistrarImpl` 的登记、开始和结束，`ChoiceAnswersService` 的整组提交，及审批、检查点、上下文、恢复任务的联合事务。数据库重试边界不得包含模型调用、命令副作用或未被回滚管理的文件发布；不能简单给已有 `@Transactional` 方法内部套重试。

### 5.4 数据目录、备份与启动

调整 `UserConfigDataDirPostProcessor` 的文件识别、`SettingsDirectoryMigrator`、`scripts/Initialize-Development.ps1` 及对应快照工具；同步检查 Electron 后端启动参数和目录说明。如果目录中存在 SQLite 数据却没有已验证的 H2 迁移结果，应明确提示尚未迁移并停止本次启动，不能静默建一个空 H2 库造成“历史消失”。真正的空目录仍按首次安装流程建库。

H2 在线库备份可参考旧 `SettingsDirectoryMigrator` 的 `BACKUP TO` 与解包方式。该命令提供库内一致性，但不能自动保证外部正文文件的一致性。[H2 备份说明](https://h2database.github.io/html/commands.html#backup)

库备份、检查点复制和回收继续处于同一静默窗口，且切换前冻结业务写入；不能把“文件写入静默”误当成“所有数据库写入都停止”。如目录复制后到重启前仍允许源库继续写入，还必须排空或阻止这些写入，否则目标会漏掉后续提交。失败时配置不切换，源数据不删除；验证恢复后的库与正文集合，而非只检查备份 ZIP 存在。

## 6. 当前 SQLite 数据迁移流程

这与历史的“新建 SQLite、不导入 H2”不同。本次默认要求保留**当前 SQLite 的全部业务数据及当前配置资源**；遗留 H2 库不自动合并。发现多个数据源冲突时明确报告，不按时间猜测哪个更新，不生成临时业务身份。

1. **确定源目录和版本**：从当前设置、后端实际连接与运行包确认源库，盘点表、主键、索引、当前 schema_version、检查点引用、JSON 配置和资源。只查看仓库配置不能证明安装版正在使用哪个目录。
2. **建立停写窗口**：先用复制数据演练。正式迁移停止应用及其他会写源目录的后端进程，确认句柄释放；保留 SQLite 主库及其伴随文件、checkpoints 和配置资源的完整可回退副本。不能复制运行中的主文件就当作完整备份。
3. **创建隔离目标**：使用全新目标目录与固定版本 H2 建当前 schema。目标已有数据库时拒绝覆盖；不能直接打开遗留 `.mv.db` 触发升级。
4. **分批迁移**：独立一次性工具通过源、目标 Mapper/PO 读取和写入；隔离在基础设施与迁移工具中，不让应用领域依赖两个数据库。保留 ID、version、generation、状态、时间、幂等键、JSON 和文本正文，不调用会递增版本或触发业务副作用的 Service。显式插入数据库生成 ID 后校准后续自增起点，并验证下一次普通插入不会撞号。
5. **搬迁正文和配置资源**：保持 executionId 与 snapshot_file 对应路径，按源引用复制并核对哈希；配置 JSON 的权威来源保持不变，只调整明确需要变化的 dataDir。保留未引用文件供审计，不在迁移中顺手清理。
6. **逐行验证**：按实际表清单核对行数、主键集合及全部持久化字段的规范化指纹，显式区分 NULL 与空串；时间以 UTC/毫秒比较，CLOB 读取内容后计算哈希。检查关系、唯一键、检查点文件引用及资源；故意改变一条正文或版本的副本，验证校验器会失败。不能以 COUNT 相等作为无损证明。
7. **关闭重开**：干净关闭目标 H2，再启动独立校验进程读取，避免只验证内存中的数据。演练阶段禁用正常启动收口、自动恢复和后台写入；不能让它们改变目标后再解释为迁移差异。
8. **发布切换**：只有候选包、迁移结果和回退副本都通过验证后，才在同一停写窗口切换包和目录配置。重启后验证会话列表、历史、当前上下文、待答组、审批、历史重发与子会话。正常启动可能执行既有任务收口规则，需记录其预期变更，不承诺旧进程的运行中任务能原地继续。

工具生成迁移清单，记录源备份指纹、引擎及脚本版本、逐表校验结果、文件清单、目标目录和验证结论；不把用户正文、密钥和完整数据库提交进 Git。中断后不能默认在半成品目标上盲目续写；首版采用新的隔离目标重新执行，保留失败目录定位问题。

生产包最终只支持 H2。迁移工具临时支持读取 SQLite，不构成运行时双写、动态换绑或双库降级。

## 7. 验证与变异门槛

以下均在独立目录与真实 H2 文件库运行。测试业务数据经 Mapper/仓储准备与读取，建表经脚本执行器；不能用内存 H2 或 Mockito 成功替代文件落盘与竞争验证。

| 验证面 | 可复用用例/新增场景 | 必须能识别的回退 |
| --- | --- | --- |
| schema、分页、时间 | 改造 `SqlitePrototypeTest`、`SqliteSchemaResourceTest`、`SqliteSchemaPoConsistencyTest`，保留扫描增量补列；增加关闭重开 | 删除 `snapshot_file` / `reasoning_effort`、遗漏唯一索引、错时区/分页后必须失败 |
| 多问题登记与回答 | `ChoiceAnswersServiceTest` 加真实并发多题登记、普通工具日志混合写入、整组回答 | 删除一题登记、部分提交成功、重复命令改答案或重复登记覆盖结论必须失败 |
| 消息与业务并发 | `TranscriptConcurrencyTest`、`ChecklistPersistenceTest`、`ExecutionResumeTaskRepositoryTest`、邮箱去重 | 去掉唯一索引、版本或代际条件后，重复事实/双领取等被检出 |
| 事务重试 | `TransactionRetryTemplateTest`、`ConcurrentCheckpointSaveTransactionTest`、`ModelContextReplaceTransactionTest` | 用 H2 实际锁冲突替换 SQLite 快照交错夹具；退回同一失效事务或拆散外层原子性必须失败 |
| 联合事务 | 整组答案、工具槽位、检查点引用、上下文、恢复登记中途注入失败 | 不得留下已答卡片但未填槽位、孤立恢复任务或指向回滚正文的引用 |
| 文件与回收 | `ConcurrentCheckpointReadAndReclaimTest`、`LocalFileCheckpointStoreTest` 及在途登记/孤儿清理用例 | 提前删除旧正文、漏登记在途文件、误删历史重发基线必须失败 |
| 目录搬迁与迁移 | `SettingsDirectoryMigratorDatabaseTest`，新增 SQLite → H2 逐行/文件校验与失败注入 | 修改 CLOB、版本、时刻或漏文件后，迁移校验必须拒绝；失败不能改变源目录配置 |
| 内存与引擎故障 | 保留 `LimitedHeapCheckpointOomTest`，增加真实 H2 混合负载与独立 panic 探针 | 回退整段检查点转换/缓存能变红；旧 2.3.232 作为 panic 正对照，不触碰用户库 |
| 应用行为 | 当前会话/子会话、补充恢复、审批、后台任务与历史重发相关回归 | 换库不能更换 ID、丢失补充、重复执行命令或破坏通知顺序 |

SQLite 的 BUSY_SNAPSHOT 交错不一定能在 H2 上成立，不能机械改测试数据库后等待旧异常。H2 用例应制造其真实写写冲突；保证只因目标缺陷回退而失败，等价变异不算证据。

受限堆验证分两层：现有流式路径守卫继续约束整段转换次数；新增 **H2 + 文件检查点 + CLOB** 的混合负载，覆盖独立执行并发保存、上下文替换和工具登记。以 512 MiB 子 JVM 对照，并以当前安装版 1 GiB 参数做长时间验证，记录峰值堆、GC、工作集、吞吐和失败类别。现有 360 MiB 守卫阈值来自旧夹具，不能无证据放宽或直接当作 H2 验收结果。

先用已知差异样本验证指纹器，用含 NUL 的故意异常日志验证扫描器，并证明覆盖全部目标文件和目录，再报告“无 OOM / 无缺失 / 无旧驱动残留”。每处缺陷修复附同批回归与有效变异，恢复后再跑相关测试。通过定向事务、并发、文件与迁移测试后执行后端全量测试、打包及安装产物检查；本次若不改前端，不新增前端功能或无关测试。

## 8. 实施顺序与提交边界

每个可独立评审的单元完成即提交，只暂存本任务文件，不把其他工作树修改、编辑器残留、私有探针或数据样本带入提交。

| 单元 | 交付 | 完成条件 |
| --- | --- | --- |
| A：H2 原型与风险验证 | 固定驱动、独立文件库原型、CLOB/时间/DDL/锁与 panic 验证 | 新 H2 + 文件正文的关键技术约束有证据；不切生产默认库 |
| B：生产适配 | H2 schema、初始化、方言、TypeHandler、异常与仓储兼容 | 当前业务与事务回归通过；文件检查点仍保留 |
| C：一次性数据迁移 | 独立迁移工具、表与文件校验器、停机和失败处理 | 复制数据全量迁移、故意变异拒绝、关闭重开及恢复行为通过 |
| D：目录与开发脚本 | H2 一致性备份、检查点集合搬迁、配置与开发初始化 | 源目标隔离、失败不切配置、备份可恢复 |
| E：终验与交付 | 并发/受限堆/全量回归记录、最终包版本与依赖核验 | 所有门槛通过后形成可部署产物，再执行正式切换 |

B/D 之间允许测试夹具同步适配，但每个提交边界要说明依赖，不能让半成品默认连接用户目录。最终包中 SQLite 驱动退出运行时；测试/迁移源数据依赖隔离在相应工具或验证范围内。

## 9. 切换与回退边界

**首次新写入之前**：停止候选程序，恢复切换前包、设置与 SQLite/正文集合，可回到相同业务时点。候选启动自带的后台写入也属于新写入，不能只看用户是否发过消息。

**H2 已接受新写入之后**：旧 SQLite 副本已经落后，直接换回会丢掉切换后的记录。首版不宣称具备在线无损反向迁移；应冻结 H2、保全当前库与文件，优先回滚到兼容同一 H2 schema 的前一应用包。若必须退回 SQLite，另行完成并验证 H2 → SQLite 数据迁移后才能切回；不能把恢复旧备份说成无损回退。

原 SQLite、旧 H2 证据与失败迁移目录保留，明确标识来源和时间，不在成功切换后自动删除。回退必须同时考虑检查点文件、JSON 配置和资源，不能只回滚 JAR 或 `.mv.db`。

## 10. 当前已核实与尚未核实

已核实：H2 移除提交及父提交可取回；文件检查点与后续修复有独立提交边界；当前反向补丁检查失败；旧 H2 事故和对照报告可追溯；候选 H2 官方版本及相关文档可访问。

尚未核实：当前安装版实际目录与数据库状态、新 H2 业务负载内存、真实工具多问题并发、全量迁移工具、H2 生产适配、最终安装包。本文不据仓库历史推断这些项目已通过，也不据本文修改任何用户数据库。
